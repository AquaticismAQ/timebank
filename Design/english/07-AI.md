# Time Bank · AI technology application solution (AI)

> This document is a sub-plan of "Time Bank Solution Design" (`01-TimeBankDesign.md`), which describes in detail the specific application, implementation path and access suggestions of AI technology in time bank. Each AI capability serves the three major goals of "authenticity verification, privacy protection, and risk control" and does not involve extended scenarios such as content generation, recommendation, or scoring. See `02-ManualAudit.md` for the calling sequence of the AI audit capability, and see `05-OnlineSystem.md` for the hosting system.

---

## 1. Positioning and panorama

The sole purpose of introducing AI technology into Time Bank is to **improve the authenticity verification capabilities of service records** and to **reduce manual review costs**. AI plays the role of "preliminary filtering layer" in the system and does not replace the teacher's final judgment and does not make evaluative conclusions for students.

```mermaid
flowchart LR
A[On-site check-in<br/>Students upload materials] --> B[End-side edge AI<br/>Real-time face desensitization]
B --> C[Cloud multi-modal AI<br/>Preliminary review of scene content]
C --> D[Image authenticity detection<br/>Reproduction/tampering identification]
D --> E[Statistical risk control engine<br/>Abnormal behavior detection]
E --> F{Comprehensive credibility score}
F -- High reliability --> G [Automatically pass → Enter the spot check pool]
F -- Zhongxin --> H [Transfer to teachers for manual second review]
F -- Low confidence/abnormal --> I[Interception → Manual audit]
```

| AI module | Technical classification | Running location | Function |
| --- | --- | --- | --- |
| Device-side face desensitization | CV (face detection) | Mobile phone local (WASM) | The original image does not appear on the device, protecting the privacy of minors |
| Multi-modal content review | CV + multi-modal LLM | Cloud (API) | Compare the consistency of submitted content with photos/videos |
| Image authenticity detection | CV (frequency domain analysis) | Cloud | Identify screen remakes, PS synthesis, EXIF tampering |
| Statistical anomaly risk control | Statistical ML | Cloud (backend service) | Detecting spatio-temporal contradictions and scoring behavior patterns |
| Witness credit scoring | Behavioral modeling ML | Cloud (backend service) | Dynamically assess scatter witness credibility |

## 2. End-side face desensitization (Edge AI · On-Device)

### 2.1 Goals and Constraints

- **Goal**: Complete facial desensitization of all minors and recipients locally on the student's mobile phone before the photo is uploaded, and the original image never leaves the device.
- **Constraints**: Must be completed within 300ms (witnesses are waiting to experience it); the model package does not exceed 2MB (mini program package body limit); supports downgrade compatibility for low-end Android models.

### 2.2 Technical solution

#### Main solution: WASM + BlazeFace (recommended)

- **BlazeFace** is a lightweight face detection model in Google MediaPipe. It is specially optimized for mobile terminals. The model size is about **400KB** and the single inference time is **< 50ms** (mid-range machine).
- Run through **WebAssembly (WASM)** in the WeChat applet, no Native plug-in is required, and it will pass the review.
- Desensitization method: After detecting the face rectangular frame, perform **Gaussian blur** (sigma ≥ 15, unrecognizable to the naked eye) or apply **cartoon mask** (little sun/little red flower, which increases interest and is irreversible) to the area within the frame.

```
┌─────────────────────────────────────────────┐
│Mobile version (WeChat mini program WASM sandbox) │
│                                             │
│ Original image (memory) → BlazeFace detection → Face frame list │
│       ↓                                     │
│ Canvas API writes Gaussian blur pixels to the area within the frame │
│       ↓                                     │
│ Desensitization picture (memory) → Upload to cloud storage │
│       ↓                                     │
│ Explicit release of original image memory (ArrayBuffer empty) │
└─────────────────────────────────────────────┘
```

#### Downgrade plan: Cloud desensitization (cover the whole story)

For models where BlazeFace fails to load or inference times out (>500ms), switch to **Desensitize and burn upon upload**:
- The client first localizes the full Gaussian blur image (pixel level, no model required), and then uploads it.
- The cloud uses Alibaba Cloud Content Security "Face Blur" interface for secondary confirmation, and the original version is deleted immediately after processing.
- The privacy intensity of this path is lower than that of the main solution. It is only used as a backup to record downgrade events.

#### Plan comparison

| Dimensions | WASM + BlazeFace (main) | Cloud desensitization (downgrade) |
| --- | --- | --- |
| Original image privacy | Optimal (no device required) | Medium (original image uploaded briefly) |
| Latency | 50–150ms (local) | 200–500ms (network RTT) |
| Cost | Zero marginal cost | Pay-per-view (about 0.1 cents/photo) |
| Compatibility | WASM support required (WeChat ≥ 7.0.0) | Compatible with all models |

### 2.3 Timing connection with witness process

In scheme A (timing isolation, see section 4.3 of `02-ManualAudit.md`), desensitization is triggered at the moment when the witness clicks to confirm:

```
The witness clicks "Agree to Witness" → onConfirm() callback
→ Activate WASM BlazeFace (preloaded)
→ Perform inference + coding on the original image in memory (< 150ms)
→ Upload masked image + SHA-256 hash
→ The original image ArrayBuffer is assigned to null and released by GC.
```

Make sure that the witness sees the original image, and what is uploaded and stored is always the desensitized image.

## 3. Multimodal content review (Cloud AI · Multimodal)

### 3.1 Goals

Compare the **service type and description declared by the student** with the **uploaded de-identified photos or short videos** to identify obvious fraud, such as claiming nursing-home companionship while submitting an image from an internet café.

### 3.2 Audit Dimensions

| Dimensions | Technical means | Examples |
| --- | --- | --- |
| Scene recognition | Image classification (location/environment label) | Recognize "park/grass/garbage bag" → match "environment clean" declaration |
| Behavior recognition | Action detection (video frame analysis) | Identify public welfare actions such as "bending to pick up/carry/wipe" |
| Object detection | Target detection (YOLO series) | Detection of cleaning tools, books, wheelchairs and other service-related props |
| Application - picture consistency | Multi-modal alignment (text + image) | To apply for "garbage classification publicity", there must be classification buckets/leaflets/public in the screen |
| Unsuitable content filtering | Content safety classification | Blocking pornographic/violent content to protect minors |
| Season-Environment Consistency | Timestamp × Vegetation/Light Analysis | GPS timestamp is December, the picture shows dark green summer vegetation → Abnormal |

### 3.3 Implementation path

#### Path A: Call the cloud vendor content security API (recommended, initial stage)

Domestic compliance mature API, ready to use out of the box, no need to build a self-built model:

| Service Provider | Recommended Products | Applicable Dimensions | Billing Reference |
| --- | --- | --- | --- |
| Alibaba Cloud | Content Security "Picture Review (Large Model Multi-modal Version)" | Scene/Behavior/Object/Uncomfortable Content | ~0.2 points/picture (after scale) |
| Tencent Cloud | Tianyu "Picture Content Security" | Scene Tags + Uncomfortable Filtering | ~0.2 points/picture |
| Alibaba Cloud | Video content review | Video frame-level analysis | ~0.5 minutes/minute |

**Calling method**: The back-end service (`05-OnlineSystem.md` audit service module) asynchronously calls the API after receiving the masked image, matches the returned label list with the declaration type, and outputs a preliminary confidence score.

```
POST desensitized image URL → Alibaba Cloud Content Security
← Return: { labels: ["park","garbage bag","cleaning behavior"], score: 0.87, risk: "none" }

Rule engine:
Declaration Type = "Environmental Cleaning"
Matching tag ∩ Declaration keyword = { "garbage bag", "cleaning behavior" } → scene consistency: passed
```

#### Path B: Private deployment of multi-modal models (mid- to late-stage, high-value certificates)

For high-value certificates linked to higher education, consider privatizing the deployment of open source multi-modal models (such as **InternVL**, **Qwen-VL**):
- Input: desensitization chart + student declaration text description
- Output: consistency judgment + summary of reasons (for teacher’s second review reference)
- Deployed in an independent instance in school or cloud, data does not leave the system

#### Path comparison

| Dimensions | Cloud API (initial recommendation) | Privatization model (high-value scenario) |
| --- | --- | --- |
| Deployment cost | Very low (zero development) | High (requires GPU or model inference service) |
| Data compliance | Data processing agreement needs to be reviewed | Complete data control |
| Capability upper limit | Subject to API capability updates | Customizable Prompt/Rules |
| Applicable stages | Stage 3 POV onwards (see `05-OnlineSystem.md`) | Stage 4 high-value certificate review |

### 3.4 Connection with AutoAudit

The **scene label list** and **confidence score** output by the multi-modal AI preliminary review are directly written into the metadata field "AI Score and Label" in Section 9.2 of `02-ManualAudit.md` for subsequent use by the risk control engine and the teacher for the second review.

## 4. Image authenticity detection (Forgery Detection)

### 4.1 Goals

Identify the following three categories of image fraud:

| Type of counterfeiting | Description | Detection methods |
| --- | --- | --- |
| **Screen Capture** | Use your mobile phone to take a photo on another mobile phone/computer screen | Moiré detection, screen border detection, brightness/color gamut abnormality |
| **P picture synthesis** | Photoshop and other tools to cut and splice backgrounds or characters | ELA (Error Level Analysis), frequency domain DFT analysis |
| **EXIF tampering** | Modify shooting time and GPS information in photo metadata | EXIF integrity check + cross-validation with server timestamp/GPS |

### 4.2 Technical details

#### Remake screen detection

- **Moire**: The frequency superposition of the display pixel array and the camera CMOS photosensitive array will produce regular moiré stripes, which can be identified by detecting high-frequency periodic peaks in the frequency domain through **DFT (Discrete Fourier Transform)**.
- **Screen Border/Reflection**: CNN target detection identifies the screen border rectangle and specular reflection features.
- **Color gamut compression**: Screen reproduction will trigger two JPEG compressions, narrowing the color gamut, and double compression characteristics can be identified through **DCT coefficient histogram analysis**.

#### P-graph synthesis detection (ELA)

**ELA（Error Level Analysis）**：
1. Re-JPEG-compress the image to be inspected with a fixed quality factor (such as Q=75).
2. Calculate the pixel difference map (error map) between the original image and the recompressed image.
3. The error level in each area of the real photo error map is uniform; the synthetic area of the P picture shows **local error mutation** (highlighted area) due to different compression histories.

It is suitable for detecting background replacement and character cutout synthesis. It has low implementation cost (pure CPU image operation) and can be built on the server side.

#### EXIF integrity check

```
Sent synchronously when the client uploads:
  - System timestamp (ms precision, server-side anti-tampering verification)
  - GPS coordinates (system level, non-EXIF readable and writable layer)

Server-side cross-validation:
1. EXIF.DateTimeOriginal ≈ Server receiving timestamp (±5min error allowed)
2. EXIF.GPSLatitude/Longitude ≈ Mini program reports GPS (±100m error allowed)
3. EXIF key field (Make/Model/Software) consistency check
→ Any discrepancy → trigger medium/low confidence mark
```

> Note: EXIF can be modified by tools, so EXIF verification is only used as an **auxiliary indicator** and is not used as a basis for interception alone. It needs to be combined with other dimensions for comprehensive scoring.

### 4.3 Access solution

- **ELA + Frequency Domain Analysis**: Can be lightweight and self-built (Python `Pillow` + `NumPy` + `scipy.fft`), deployed as an internal HTTP microservice, single processing < 100ms, extremely low cost.
- **Screen Capture CNN**: You can call the "screenshot detection" capability of Tencent Cloud/Alibaba Cloud Image Quality Assessment API, or use the open source model **MantraNet/Noiseprint** for self-deployment.

## 5. Anti-Fraud Statistical Engine

### 5.1 Design ideas

Drawing from the financial industry’s **anti-money laundering (AML)/anti-brushing** model: individual cheating behavior can simulate isolated evidence, but **cannot falsify statistical laws on a large scale**. The risk control engine jointly scores through multi-dimensional exception rules, puts a "risk label" on a single record, and imports it into the `02-ManualAudit.md` credibility scoring framework.

### 5.2 Detailed explanation of rules

#### Rule 1 · Metcalf Dispersion Filtering

**Principle**: The witnesses, locations, and times of real spontaneous public welfare should be highly **randomly discrete**; the witness chain of family or gang cheating should be **highly clustered**.

```
Calculated indicators:
D_witness = distinct(witness_phone_prefix) / total_records // Witness the dispersion of mobile phone number segments
D_location = stddev(GPS) / mean_dist // Location standard deviation
D_time = entropy(weekday_distribution) // Check-in week distribution entropy value

Trigger conditions (example threshold, need to be tuned based on actual data):
  - In the 20 records in the past 90 days, the same witness mobile phone number appears ≥ 5 times → Orange alert
  - Witness UnionID Hash is related to the student in the WeChat relationship chain P > 0.8 → Red Alert
  - D_location < 0.2 (almost all public interests are within the same 500m range) and D_witness < 0.3 → Yellow Alert
```

#### Rule 2 · Frequency Fence (Velocity and Frequency Fence)

| Detect Dimensions | Rules | Trigger Actions |
| --- | --- | --- |
| Witnesses cross-student high frequency | The same witness mobile phone number signed for ≥ 3 unrelated students within 7 days | Determined as a "professional witness", the account was blocked, and the associated records were downgraded |
| Witnesses are fixedly bound | More than 90% of the witnessing behaviors of a certain witness account point to the same student | It is judged as an "exclusive family cheating account" and triggers manual verification |
| High-frequency student thrusts | The number of records submitted by a single student in a single week exceeds the average by 3σ | Orange alert, transfer teacher review |

#### Rule 3 · Geo-Temporal Fencing

```
Two punch-in records before and after:
Δt = t2 - t1 (minutes)
Δd = haversine(GPS1, GPS2) (km)

Physically feasible speed = Δd / Δt × 60 (km/h)

  > 120 km/h (driving + walking limit) → red interception (time and space conflict, backward date filling/fake GPS)
  > 60 km/h (bicycle limit) → Orange warning (manual verification required)

Special treatment: Exemption is provided when there are subway/high-speed rail travel records (linked with traffic data, optional) in the record room.
```

#### Rule 4 · Seasonal and Environmental Consistency

Cross-validation of **vegetation/light/meteorological labels** output by multimodal AI (Section 3) with **system timestamp + GPS urban climate data**:

| AI image tag | Check in time/place | Judgment |
| --- | --- | --- |
| Dark green leaves, summer light | Example City · January | Time contradiction → Red interception |
| Snowy ground | Example City · July | Location/time conflict → Red interception |
| Indoor scenes, no public welfare props | Application: Clean outdoor environment | Conflicting scenes → China Trust, transfer to second instance |

Implementation: Maintain a **Example City monthly climate template** (monthly average vegetation status, sunrise and sunset time windows), and perform simple rule matching with AI scene tags without the need for additional models.

### 5.3 Comprehensive scoring model

Each rule outputs a 0-1 risk score, which is weighted and fused into the final **Trust Score**:

```
TrustScore = w1 × SceneConsistency // Multi-modal scene consistency
+ w2 × ForgeryClean // Remake/P picture detection passed
+ w3 × ExifConsistency // EXIF verification passed
+ w4 × GeoTemporalFeasible // Space-time feasibility
+ w5 × WitnessDispersal // Witness dispersion
+ w6 × FrequencyNormal // Frequency is normal
+ w7 × SeasonConsistency // Seasonal environment consistency

Initial recommendation weight (w1–w7) = [0.25, 0.15, 0.10, 0.15, 0.15, 0.10, 0.10]
(The weight should be continuously adjusted based on the false positive rate and missed negative rate after going online)

TrustScore ≥ 0.8 → High trust, automatically passed
0.5 ≤ score < 0.8 → Medium credibility, second review for transfer to teacher
score < 0.5 → low confidence, interception warning
```

## 6. Witness Credit Scoring

### 6.1 Objectives

Conduct **dynamic credibility profiling** on scattered passerby witnesses who cannot be pre-bound to the whitelist to prevent "professional witnesses" and "family cheating chains".

### 6.2 Credit score model

Each witness (identified by mobile phone number Hash + UnionID Hash) maintains a **credit score (0–100, initial 60)**:

| Event | Credit Score Change | Description |
| --- | --- | --- |
| First time witnessing, final record passed | +5 | Normal witnessing behavior |
| The witness record was confirmed and approved by the teacher in the second review | +3 | Further confirmed to be credible |
| The student record witnessed this time was intercepted/rejected | -10 | Risk of associated record fraud |
| Witnessed ≥ 3 unrelated students within 7 days | -20 | Abnormal frequency |
| The time and space of the witness does not match the GPS of the student’s check-in | -15 | Not at the scene |
| Confirmed to be a false witness after manual verification | Clear + permanent blacklist | |

### 6.3 The impact of credit score on credibility

```
WitnessFactor = min(1.0, WitnessCredit / 80)

// WitnessCredit = 60 → WitnessFactor = 0.75 (normal witness, small reduction)
// WitnessCredit = 80 → WitnessFactor = 1.0 (high credibility witness, full weight)
// WitnessCredit = 30 → WitnessFactor = 0.375 (low-credibility witness, substantially reduced weight)

// WitnessFactor is substituted into the w5 sub-item of TrustScore in Section 5.3
```

### 6.4 Joint credit and deterrence mechanism

- Once cheating is verified, the joint credit points of **student account + endorsing guardian + peer group members** will be reduced simultaneously (see Section 7.2 of `02-ManualAudit.md`).
- The system displays at the bottom of the witness confirmation page: "This certificate has been stored on the blockchain, and about 2% of the witnesses will be randomly called back for a follow-up visit." This creates psychological shock at a very low cost (the actual call-back is undertaken by volunteers from the Family Committee, and each time only takes 10-20 seconds).

## 7. Access recommendations and cost estimates

### 7.1 Recommended access solutions for each module

| Module | Recommended solution | Alternative solution | Recommended access stage |
| --- | --- | --- | --- |
| On-device face de-identification | WASM + BlazeFace (self-integrated) | Cloud de-identification (fallback) | Phase 3 |
| Multi-modal content review | Alibaba Cloud Content Security Image Review API | Tencent Cloud Tianyu / Privatized InternVL | Phase 3 |
| Image authenticity detection | Self-built ELA + frequency domain service (Python) | Tencent Cloud image quality assessment API | Third stage |
| Statistical risk control engine | Self-built rule engine (backend service) | No SaaS replacement, must be built by yourself | Phase 3 |
| Witness credit score | Self-built credit score service (DB reading and writing) | No SaaS replacement, must be self-built | Phase 3 |

### 7.2 Cost Estimation (Reference for the Whole School Scale)

Assuming 500 students per academic year, each submitting an average of 30 records, totaling **15,000 records/year**:

| Expenses | Unit price (estimate) | Annual fee (estimate) | Description |
| --- | --- | --- | --- |
| Alibaba Cloud image content review | ¥0.002/image | **≈ ¥30** | 15,000 de-identified images |
| Alibaba Cloud cloud desensitization (downgrade trigger is about 5%) | 0.1 points/photo | **≈ ¥1** | ~750 photos downgraded |
| Self-built ELA server computing power | Shared 2-core CPU | **≈ ¥100/year** | Lightweight microservices, no GPU required |
| Witness credit score / risk control DB | Database reading and writing | **< ¥50/year** | Attached to the main business database |
| **Total** | | **≈ ¥180/year** | Very low marginal cost |

> The above estimate does not include basic server and database costs (already included in the `05-OnlineSystem.md` architecture cost).

### 7.3 Precautions for landing

1. **BlazeFace WASM preload**: The WASM module is silently loaded in the background when the mini program is started, ensuring that there is no perceived delay when the check-in page is used for the first time.
2. **Cloud API Data Processing Agreement**: Before calling the Alibaba Cloud/Tencent Cloud content security API, confirm that its data processing agreement (DPA) meets the requirements of the Personal Information Protection Law; desensitized images cannot identify individuals, and compliance risks are low.
3. **Risk control rule version management**: Rule thresholds (such as "witnessing ≥3 students within 7 days triggers demotion") should be configurable and rollable to avoid misjudgments leading to a surge in student complaints.
4. **AI misjudgment appeal channel**: The system must retain the "Submit appeal against AI interception results" entry, and all intercepted records will be retained for 30 days for manual review (see Section 12 of `02-ManualAudit.md`).
5. **Model update strategy**: Alibaba Cloud API capabilities will be iterated regularly, and self-built ELA/frequency domain services do not need to be updated; the BlazeFace model version is fixed in the mini-program package, and changes need to be reviewed again.

## 8. Privacy and Compliance

| Principles | Implementation methods |
| --- | --- |
| The original image cannot be exported from the device | The original image is destroyed after desensitization on the client side, and only the SHA-256 hash is uploaded to the chain (see `04-Blockchain.md`) |
| Minimize data transmission | The multi-modal API only passes in the desensitized image URL, not the original image; the image will be deleted immediately on the cloud provider's side after the API request (contract agreement) |
| AI results are not directly qualitative | AI scores are only used as "preliminary review suggestions", and the final review rights belong to teachers; AI tags are not archived for individual students |
| Special protection for minors | After the desensitized image is processed by BlazeFace, the face is no longer identifiable; even if the data is leaked, the student portrait cannot be restored |
