# 学生身份标识设计

> 本文描述学生在系统中的两个标识——**登录名**与**学号**——各自的形态、由来与边界，
> 以及学校在导入前如何准备名册 CSV。**首次登录、激活码与凭证单不在本文**，见
> `10-StudentActivationFlow.md`。
> 改动本文时请同步更新 `Design/english/09-StudentIdentity.md`。
> 相关文档：掩码约定与身份鉴别见 `08-mlps-level1-security-design-guide.md` §4／§8；
> 导入流程见 `12-DataImport.md`；决策记录与被否决的替代方案见
> `Docs/optimization/10-StudentIdentityAndOnboarding.md`。

---

## 1. 这份设计要回答的问题

一名学生在系统里有两个标识，而它们**刻意不是同一个**：

| 标识 | 是什么 | 谁生成 |
| :--- | :--- | :--- |
| **登录名** `username` | 他登录时输入的东西 | 系统，在导入时 |
| **学号** `studentNumber` | 名册主键，服务记录编号的一部分 | 学校，在导入之前 |

把两者合一是最自然的想法，也是本设计明确否决的（§2）。分开之后才有一条能一句话说清
的性质：**学号可以印在纸上、显示在屏幕上、写进记录编号，因为它不能用来登录。**

---

## 2. 登录名：8 位随机数字

学生登录名形如 `48215577`：`10000000`–`99999999` 之间的**随机**数字，以**字符串**存储，
**终身不变**。教职工保留 `teacher001` 形式。两者共用**同一个命名空间与同一个唯一索引**。

### 2.1 三条容易被"优化"掉的约束

| 约束 | 一旦违反会发生什么 |
| :--- | :--- |
| **随机，不是顺序** | 顺序号泄露入学顺序与班级规模，正是 §2.2 否决顺序方案的理由本身 |
| **无前导零** | `00482155` 在任何人用电子表格打开名单的那一刻变成 `482155` |
| **以字符串存储** | 存成整数会同时带回上面两个问题，并与 `teacher001` 产生类型冲突 |

### 2.2 被否决的三种方案

- **顺序号（`student001`…`student52834`）**：随规模变丑，且泄露入学顺序与总量。
- **直接用学号登录**：Crockford 字符串比任何基于姓名的方案都更难记，并且把名册主键
  与登录凭证耦合在一起——§1 的那句性质将不再成立。
- **由英文名派生（`Alex L.` → `alex3254`）**：这是最易记的方案，经过了几轮讨论才被
  否决。它对**没有拉丁名的学生无解**，而每一种补救都比问题本身更糟：拼音转写需要姓氏表、
  多音字例外表（單读 Shàn 不读 dān，解读 Xiè，曾读 Zēng）与复姓表（欧阳、司马、诸葛），
  并且仍会猜错——**把一个关于学生自己名字的错误印在纸上，比一个从不声称知道名字的
  标识更糟**。从词表里分配一个则等于凭空给学生造一个他没有的英文名，且因系统不存性别，
  词表还必须是性别中立的。

**已接受的代价是明确的**：8 位随机数字确实比 `alex3254` 难记——一个词块加四位数字，
好过四组两位数字。换来的是一条规则：没有词表、没有音译、没有"这部分学生走另一套"的
回退人群，也没有学生来问自己为什么叫 Maya。数字还有三个附带好处：在手机数字键盘上
好输入、不泄露姓名、抗枚举（知道一个名字之后，攻击面是 10⁸ 而不是 10⁴）。

### 2.3 登录只接受登录名一种标识

不做"先按登录名、再按学号、再按工号"的回退匹配。同一个输入值可能命中甲的登录名与
乙的学号，回退顺序一旦判断有误，登入的就是别人的账号（`08-...` §8.1）。

登录名比对不区分大小写——数据库排序规则本身如此，因此 `Alex3254` 与 `alex3254`
从一开始就不可能并存。

## 3. 学号：Crockford base32，且不是凭证

学号由**学校生成，在进入系统之前**完成。系统只校验格式与唯一性，**不生成学号**。

- **字母表刻意剔除 I、L、O、U**，避免与 1、0 混淆——这个值要被教师在屏幕上读取、
  打印在卡片上、再手工回填录入。
- 8 位可表示约 1.1×10¹² 种取值；5000 名学生规模下碰撞概率约二十二万分之一
  （同规模的 8 位十六进制约为三百四十分之一）。
- 系统对学号建立唯一性约束：碰撞导致导入失败并明确报错，**不会静默覆盖数据**。

### 3.1 一条硬性要求：终身稳定

**不得按学年或按批次重新生成学号。** 服务记录编号形如
`TB-{学年}-{年级}-{学号}-{序号}`，学号直接构成编号的一部分。若同一学生的学号发生变化，
已发放的记录编号、历史记录关联与后续增量导入的匹配会同时失效。

这条要求落在学校侧——系统无法检查"这个值和去年是不是同一个"。§5.6 的离线工具因此
必须可重跑且结果稳定。

### 3.2 不建议带星号的掩码学号

如 `******24`：末位若干数字的取值空间过小，数百人规模下必然碰撞，且星号进入记录编号
后会损害其唯一性与可读性。

### 3.3 学号不是凭证

学号显示在管理端、印在凭证单上、进入服务记录编号。**即使外泄也无法据以登录**，因为
登录需要登录名与密码，而学号既不是登录名（§2.3 不做回退匹配），也不是密码。

## 4. 姓名：在进入系统之前完成掩码

系统**不接收学生的完整真实姓名**。学校在导入前按 `08-...` §4.1 的约定脱敏：

| 字段 | 约定 | 示例 |
| :--- | :--- | :--- |
| `displayName` | 中文名隐去中间字；英文名保留名与姓氏首字母 | `Alex L.(李*红)` |

中英文两部分采用**一致的掩码强度**，避免"中文已掩码而英文仍可直接识别"。

**系统不校验掩码强度，也无法校验**——它收到的本就只是一个字符串。这条约定由学校在
导入前执行，§5.6 的工具是为了让它可执行，而不是为了让系统代为判断。

## 5. 名册 CSV 怎么准备

### 5.1 一行等于什么

一行 = 一名学生 = **一条名册记录 + 一个无密码、待激活的登录账号**。账号在学生用激活码
首次进入之前无法登录（`10-StudentActivationFlow.md` §3）。

### 5.2 列

**表头必须逐字匹配，且顺序不可调换**（§5.3 第 1 条）。

| 列名 | 含义 | 取值要求 | 示例 |
| :--- | :--- | :--- | :--- |
| `studentNumber` | 学校生成的稳定学号 | Crockford base32（数字与字母，不含 I、L、O、U），不超过 32 字符；文件内唯一，且不得与系统中已有学生重复 | `HKTZ4HKV` |
| `displayName` | 掩码后的姓名 | 必填，不超过 100 字符 | `Alex L.(李*红)` |
| `gradeId` | 年级标识 | 必须是系统中已存在的值 | `grade_6` |
| `classId` | 班级标识 | 必须存在，**且隶属于所填写的年级** | `class_6A` |
| `enrollmentAcademicYearId` | 入学学年标识 | 必须是系统中已存在的值 | `ay_2025_2026` |
| `graduationYear` | 预计毕业年份 | 不早于 2000 的整数 | `2032` |
| `joinedAt` | 入学日期 | `yyyy-MM-dd` | `2026-09-01` |

**用户名、密码、角色都不在列中，也不可指定**：它们分别由 §2、`10-StudentActivationFlow.md`
与 `11-RolesAndPermissions.md` 决定，不是名册文件的内容。

### 5.3 三件最容易出错的事

1. **表头必须逐字且按顺序匹配。** 表头不符的文件在第 0 行整份被拒，并给出"缺了哪些列、
   多了哪些列"。系统**不会按位置猜列**——按位置解析正是"姓名进了年级列而全程没有报错"
   的成因。
2. **`gradeId`／`classId`／`enrollmentAcademicYearId` 是系统内部标识，不是"六年级""6A班"。**
   它们的真实取值来自这套系统本身：从管理端的年级／班级维护界面读取，或直接下载
   `GET /imports/templates/students` 的模板（模板与校验规则同源，不可能各说各话）。
3. **`classId` 必须隶属于同一行的 `gradeId`。** 这是跨列校验：班级存在、年级存在，
   但两者对不上，仍然是错误行。

### 5.4 文件本身

| 项目 | 要求 |
| :--- | :--- |
| 编码 | UTF-8 |
| 分隔 | 逗号；按 RFC 4180 处理引号——**姓名中含逗号时必须整格加引号**，否则列会错位 |
| 上限 | 5,000 行 / 5 MiB |
| 被拒绝的内容 | 以 `=`、`+`、`-`、`@`、制表符或回车开头的文本字段（表格公式注入）；NUL 与其他控制字符；双向文本覆写字符（如 U+202E） |

### 5.5 整份文件全部有效才会导入

**任何一行不合格，整份文件都不会导入**——不存在"跳过坏行、导入其余"这种结果
（`12-DataImport.md` §3.2、§8）。

这一条直接决定了准备工作的目标：**零错误，而不是"错几行没关系"**。校验阶段会逐行、
逐列给出稳定的错误码与说明，修正后重新上传即可；在全部通过之前，系统里不会多出任何
一名学生。

### 5.6 离线转换工具（计划中，尚未实现）

学校手里的名册是**真实姓名 + 真实学号**。本系统要的是**掩码姓名 + Crockford 学号**。
这一步转换刻意留在学校侧、系统之外：系统自始至终不持有可直接识别到个人的信息
（`08-...` §4.1），而只要转换发生在系统内部，这句话就不再成立。

计划提供一个**离线运行**的转换工具，读入学校现有名册（Excel／CSV），产出两份东西：

| 产物 | 去向 |
| :--- | :--- |
| 导入用 CSV（§5.2 的七列） | 上传到本系统 |
| **对照表**：真实姓名／真实学号 ↔ 掩码姓名／本系统学号 | **留在学校**，不进入本系统 |

对照表是学校的资产，也是学校的责任：正因为它存在，系统侧持有的是**去标识化**数据而非
匿名化数据（`08-...` §1.3 第 3 条）。

工具必须满足三条，否则它解决的问题会变成它制造的问题：

1. **学号生成稳定且可重跑**——同一名学生第二次运行必须得到同一个学号（§3.1）。因此
   学号不能随机生成后丢弃，工具要么从对照表续写，要么由确定性映射产生。
2. **离线运行，不联网。** 它处理的是全校学生的真实身份。
3. **对照表与导入文件分开输出**，避免真实身份随导入文件一起被上传。

**在此工具实现之前**，学校按 §5.2 自行准备文件，§3.1 的稳定性由学校保证。本节先行写入
设计，是因为它决定了工具的形态；`Docs/backlog/` 是这类"已定形态、尚未动工"工作的去处。
