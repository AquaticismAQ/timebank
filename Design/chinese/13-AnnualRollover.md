# 学年升级与毕业流程设计

> 本文描述每学年执行一次的升年级与毕业流程，以及两个学段之间的衔接方式。
> 改动本文时请同步更新 `Design/english/13-AnnualRollover.md`。
> 相关文档：角色与权限见 `10-RolesAndPermissions.md`；导入见 `11-DataImport.md`；
> 导出中的年级推导依赖本文定义的学段模型，见 `12-DataExport.md` §5。

---

## 1. 这份设计要回答的问题

系统里**没有任何代码会让学生升一个年级**。`student.grade_id` 自名册导入之后
再未被改写，`StudentStatus` 枚举里的 `GRADUATED` 从未被任何路径写入。

这不是一个可以继续推迟的缺口，因为其他设计已经依赖它成立：

- `12-DataExport.md` §5 按入学年份推导某学年的年级。这条推导**只有在每年确实有
  流程推进过 `grade_id` 时才与现实一致**——否则推导出的年级与库里存的年级会逐年
  分叉，而两者都会出现在同一份导出里。
- 时间币的年度要求按学年计算。学年翻篇而年级不变，等于所有学生停留在同一个年度
  要求上。
- 留存清理按毕业年份执行，而没有任何东西会把学生标记为已毕业。

---

## 2. 两个学段，不是一条六年直线

本校为六至十二年级，按**两个学段**组织：

| 学段 | 年级 | 年限 |
| :--- | :--- | ---: |
| 第一学段 | 6、7、8 | 3 年 |
| 第二学段 | 9、10、11、12 | 4 年 |

> **实现前提**：`grade` 表目前只有 `grade_6` 至 `grade_11`，**没有 `grade_12`**。
> 本设计按六至十二年级描述，因此落地时需先补上该年级行，并同步 `integration-test`
> 的种子数据（其 `graduationYearFor` 仍按读到十一年级、六年一贯推算）。
> 规则版本中初中／高中的分界在八年级，与两个学段一致，无需改动。

### 2.1 八年级升九年级**不是升级，是毕业加重新入学**

这是本设计最重要的一条决定。

八年级结束时，学生从第一学段**毕业**；九年级学生由学生发展中心**作为新生重新导入**，
学号重新分配，时间币与服务时长**一律从 0 开始**。

**为什么不把记录迁移过去**：跨学段迁移在现实里不可靠——

- 学号会变；
- 班级命名方式在第二学段可能重来一套；
- 一部分学生在八年级之后就离开了本校。

在这三件事同时成立的情况下，"把旧记录接到新身份上"需要一次人工对账，而对账错误的
后果是把一名学生的服务时长记到另一名学生头上。**与其自动做一件会出错的事，不如
明确不做。**

### 2.2 代价与其边界

代价是真实的：一名从六年级读到十二年级的学生，在系统里是**两条学生记录、两个学号**，
其第一学段的时长不计入第二学段的累计要求。

这与规则设计并不冲突：年度要求与累计要求本来就**按学段划分**（初中 25h/年、
75h 累计；高中 75h/年、300h 累计）。第二学段的累计要求衡量的就是第二学段的服务，
从 0 开始正是它的本意。

## 3. 学年翻篇当天自动执行

流程**在新学年开始时自动运行**，无需有人记得点按钮，并产出一份报告。

**翻篇日期可配置**，默认 9 月 1 日（`TIMEBANK_ACADEMIC_YEAR_START`，格式 `MM-DD`）。
9 月 1 日是惯例而非法律——学校可能提前或推后一周——该日期只决定两件事：
今天属于哪个学年，以及本流程所创建学年的起止日期。已经存在的学年保留其创建时的
日期，而所有按学年限定数据的查询读的都是这些已存的日期，因此调整边界永远不会
重新解释学生已经有记录的那些学年。

若配置值无法解析，应用拒绝启动，而不是回退到默认值——让一所要求 8 月 20 日的学校
悄悄晚升学十二天，比起不启动要糟糕得多。`02-29` 被直接拒绝：它在四年里有三年不存在，
定在那一天的流程根本不会触发，会有一整届学生没有升年级，而且没有任何提示。

> **实现说明**：定时任务每天检查一次，而不是把 cron 钉死在翻篇日期上。
> 一年只触发一次的任务只有一次机会，若那一晚服务器恰好在重启或宕机，
> 就没有人升年级、也没有任何东西说出这件事，下一个信号会是某位老师发现班级名单
> 差了一整年。每日检查的可观察行为仍是「在翻篇当天发生」，区别只在于错过的那一晚
> 会在次日补上，而不是被静默丢掉。

```
① 确定目标学年（翻篇日期所属的学年）
        │
        ▼
② 幂等检查：该学年是否已执行过？
        │  已执行 → 不做任何写入，产出说明原因的报告，结束
        ▼
③ 为目标学年创建班级行（沿用上一学年的班级后缀，见 §4）
        │
        ▼
④ 逐个处理在册（ACTIVE）学生：
        │   6 → 7      升级，班级沿用
        │   7 → 8      升级，班级沿用
        │   8          **毕业**（第一学段结束）
        │   9 → 10     升级，班级沿用
        │  10 → 11     升级，班级沿用
        │  11 → 12     升级，班级沿用
        │  12          **毕业**（第二学段结束）
        ▼
⑤ 将目标学年标记为当前学年（is_current）
        ▼
⑥ 产出报告：升级人数、毕业人数、跳过人数及原因
```

### 3.1 毕业时发生什么

- `student.status` 置为 `GRADUATED`——**这是系统中第一处真正写入该值的地方**。
- `student.grade_id` **保持不变**，仍是毕业时所在的年级。它记录的是"这名学生念到
  哪一年级为止"，而不是一个不存在的"第十三年级"。
- 该学生的**登录账号被停用**。一名学生在同一时刻只应持有一个可用身份
  （`12-DataExport.md` 的毕业生口径同此）。
- 服务记录、时间币账户与审核历史**全部保留**，可继续被教职工查询。

### 3.2 六年级与九年级从哪里来

这两个年级**不由本流程产生**。它们是两个学段的入口，由学生发展中心通过
**名册导入**（`11-DataImport.md` §2.1）建立。

因此翻篇流程跑完之后，六年级与九年级是空的，直到导入完成为止。
这是正确状态，不是故障——报告中应明确写出"六年级 0 人、九年级 0 人，等待名册导入"，
而不是让人自行发现。

### 3.3 自动执行的约束

自动执行意味着没有人在旁边看着，因此：

- **整个流程在单个事务内完成。** 不存在"升了一半"。
- **幂等，按学年加锁。** 同一学年重复触发不产生第二次写入。
- **失败时不做部分写入，并产出失败报告。** 失败不是静默的。
- **流程只改写"当前状态"，不改写历史事件**——哪些跟着改、哪些不改，见 §3.4。

### 3.3.1 失败之后还剩下什么，以及如何恢复

无人值守的意义不在于「它能不能跑通」，而在于「它没跑通的第二天早上，什么是真的」。

**失败的运行不改变任何数据。** 整个流程是一个事务，因此进程被杀、数据库连接断开、
中途发生故障切换，花名册都与开始前完全一致——没有学生走到一半，也不会有一届学生
毕业了却没有人升上来。后面所有的恢复手段都建立在这条性质之上。

**失败的运行会留下记录。** 这次尝试、它的错误与时间戳被写入 `annual_rollover_run`，
并且能在回滚之后存活。这一点必须明说，因为它并非自动成立：失败记录必须在工作事务
**结束之后**写入——写在一个即将回滚的事务里，它会跟着一起消失。运维人员面对一所
没有升年级的学校时，应该找得到比沉默更有用的东西。

**失败的学年不算已完成的学年。** 幂等性以「成功运行」为准，因此一次失败让该学年
保持开放，第二天夜里的运行会接着处理。重试不需要任何人先手工清理状态。

**成功与它所描述的工作一同提交。** 这是上一条的反面：`SUCCEEDED` 行绝不能在它声称的
升年级已被回滚的情况下提交。若成功记录写在被回滚的工作之上，幂等检查会认为该学年
已完成，于是这所学校将永远不会被升年级——悄无声息，且无法挽回。因此：**尝试**的
证据要能在回滚中存活，**成功**的声明不能。

**撤销一次已完成的运行需要变更前状态，因此系统会记录它。** 上述保护针对的都是
「失败的运行」，对「基于错误输入却成功的运行」无能为力——翻篇日期配置错误、
班级后缀不匹配导致某一届被跳过。这样的运行会干净地提交，而幂等保护随后会挡住
纠正性的重跑。由于年级、班级与状态都是原地覆盖，流程因此在同一事务内记录每位
被改动学生的原年级、原班级与原状态，使该次运行可以作为一次范围明确的操作被撤销。
没有这份变更前记录，唯一的恢复方式就是整库还原——为了撤销几百行上的一个字段，
把期间发生的其他一切（服务记录、审核、账户流水）一并丢弃。

这份变更前记录，以及消费它的撤销操作，规格见
`Docs/backlog/02-RecoverableAnnualRollover.md`，其中包括撤销**必须拒绝**的条件：
一旦有数据已经基于新花名册产生，把它还原回去就会与既有的行相矛盾。

### 3.4 哪些年级快照跟着改，哪些不改

年级与班级**不只存在学生表上**。它们被冗余写到了六张表，而数据范围过滤读的是
**每张表自己的那一列**，不是学生表的现时年级（`ServiceRecordScopeFields`、
`CaseScopeFields`、`AccountScopeFields`、`ProposalScopeFields` 取的都是
`root.get("gradeId")`）。

因此升年级必须先回答一个问题：这些快照跟不跟着改？答案按**当前状态**与
**历史事件**划分：

| 表 | 性质 | 升年级时 |
| :--- | :--- | :--- |
| `student` | 当前状态 | **改写** |
| `account` | 当前状态（每生一行，持有余额） | **改写** |
| `service_record` | 历史事件 | 不改 |
| `case_record` | 历史事件 | 不改 |
| `event_proposal` | 历史事件 | 不改 |
| `class` | 结构（按学年） | 新建当年行，见 §4 |
| `grade_*_summary` | 已按 (年级, 学年) 建键 | 不改 |

**`account` 必须跟着改，这一条最容易漏。** 时间币账户不是一条历史记录，
而是一个持续存在的当前状态。若其 `grade_id` 停留在旧年级，升年级完成的那一刻，
教师就对自己本班学生的账户失去访问——数据没丢，只是落在了范围之外，
而表现出来是"学生的账户不见了"。

**历史事件不改，是因为它们记录的就是当时的年级。** 一条八年级时产生的服务记录，
其 `grade_id` 就应当是八年级；把它改成九年级，等于篡改这条记录发生时的事实，
也会让往年的年级统计在事后发生变化。

## 4. 班级如何延续

班级行是按学年存放的（`class.academic_year_id`），因此新学年需要新的班级行。

**学段内，班级后缀沿用**：

```
9A      →  10A
9-Mars  →  10-Mars
```

年级前缀前进一位，后缀（`A`、`B`、`Mars`、`Luna`）原样保留。流程为目标学年创建
对应的班级行，并把学生移入同后缀的新班级。

**学段之间不沿用。** 第二学段的班级命名可能与第一学段完全不同，而九年级本就是
重新导入的新生，其班级由名册文件指定。

### 4.1 这条规则的适用前提

沿用后缀意味着**一个学段之内不重新分班**。若学校在学段中途重新分班，流程给出的
班级就是错的——而且是安静地错。这一点已经明确接受：学校的实际做法是学段内保持
班级稳定，在第二学段开始时重新命名一套。

若将来确有学段中途重新分班的需要，正确做法是**用名册导入覆盖班级分配**，
而不是让本流程去猜。

## 5. 与年级推导的关系

`12-DataExport.md` §5 按入学学年推导某一学年的年级。本流程是那条推导保持成立的
前提：**每年推进一次 `grade_id`，库里存的年级才会与推导出的年级一致。**

两者因此互为校验：

```
推导年级（当前学年） == 存储的 grade_id
```

不相等只有两种可能——某一年的流程没有执行，或该学生出现了留级／跳级。
报告中应当包含这项一致性检查的结果；它是唯一能在事后发现"某年漏跑了"的信号。

### 5.1 入学年级由推导得出

学生可能从六年级入学，也可能从九年级入学，因此"入学时的年级"不是一个常数：

```
入学年级 = 当前年级 − (当前学年起始年 − 入学学年起始年)
```

该值必为 6 或 9。第一学段学生在 Y 学年的年级为 `6 + (Y − 入学学年)`，
第二学段为 `9 + (Y − 入学学年)`。

## 6. 毕业生的留存

`graduation_year` 的含义是**离开所在学段的那一年**：第一学段学生为读完八年级的
那一年，第二学段学生为读完十二年级的那一年。名册导入必须与该学段一致地填写它。

留存沿用现有策略，不另设规则：**既有的毕业生清理作业按 `graduation_year` 执行，
在毕业年次年的 8 月 31 日之后清除该生数据。**

> **必须知道的后果**：第一学段毕业生的服务历史，在读完八年级后**约一年**即被清理。
> 也就是说"毕业后仍可查询"这件事成立的窗口是一年，而不是永久。这是沿用现有留存
> 策略的直接结果，已被明确接受；若将来希望第一学段的历史保留更久，需要单独调整
> 留存策略，而不是在本流程里特殊处理。

## 7. 报告内容

流程无人值守，报告是唯一的输出，因此它必须能独立说明发生了什么：

| 项 | 说明 |
| :--- | :--- |
| 目标学年 | 例如 `2027-2028` |
| 执行结果 | 已执行 / 因已执行而跳过 / 失败 |
| 升级人数 | 按年级分列 |
| 毕业人数 | 分别列出第一学段与第二学段 |
| 账户快照更新数 | §3.4 中随年级改写的 `account` 行数 |
| 跳过人数与原因 | 非在册状态、无班级、无法匹配班级后缀 |
| 空年级提示 | 六年级与九年级待名册导入 |
| 一致性检查 | §5 的推导年级与存储年级是否一致 |

---

## 8. 刻意不做的事

- **不做留级与跳级。** 系统不建模这两件事；确有需要时由管理员手工调整该生年级，
  并接受 §5 的一致性检查会对这名学生报出不一致。
- **不跨学段迁移记录。** 理由见 §2.1。
- **不自动重新分班。** 沿用后缀，其余交给名册导入。
- **不自动清理毕业生数据。** 留存由既有的毕业生清理作业负责，两者是不同的流程，
  不应合并——升级流程每年跑一次且必须成功，清理流程涉及不可逆删除。
- **不由前端触发。** 本流程按日历自动执行；它不是一个按钮。
