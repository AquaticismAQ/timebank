# 学生账号激活流程设计

> 本文描述学生从名册导入到首次登录的完整流程，以及承载首次凭证的**激活凭证单**。
> 改动本文时请同步更新 `Design/english/09-StudentActivationFlow.md`。
> 相关文档：安全与合规依据见 `08-mlps-level1-security-design-guide.md` §8.3（密码规则见 §8.2）；
> 决策记录与被否决的替代方案见 `Docs/optimization/10-StudentIdentityAndOnboarding.md`。

---

## 1. 这份设计要回答的问题

学生是**批量导入**的，不是逐个由管理员在表单里创建的。由此产生一个必须回答的问题：
一名刚被导入的学生，**第一次**怎么进入自己的账号？

传统答案是"由系统生成初始密码并发给学生"。本设计不这样做。理由是一旦服务端生成密码，
系统中就必然在某一时刻存在密码明文——需要传递、需要留存、需要销毁，而这三件事都会出错。

**本设计的核心选择：服务端自始至终不生成密码。** 学生凭一次性**激活码**首次进入，
并在激活时自行设置密码。

---

## 2. 角色与权限边界

| 角色 | 在本流程中可做的事 |
| :--- | :--- |
| 管理员（admin／sysadmin） | 导入名册；为某个班级签发凭证单；为单个学生重新签发（即"密码重置"） |
| 教师 | **无任何凭证签发路径**，包括本班学生。教师发现学生未激活时，需转由管理员处理 |
| 学生 | 使用凭证单激活账号并自设密码 |

教师不参与签发是刻意的：凭证单是系统中唯一承载可用凭证的产物，把它的签发限制在单一角色上，
意味着只有一处权限需要审计，且凭证路径上**不存在数据范围（data scope）判断**——数据范围
判断错误在报表接口上只是多看到一份名单，在这条接口上却是凭空签发登录凭证。

代价是真实存在的：发现"某学生一直没激活"的通常是班主任，而重新签发必须绕行管理员。
此代价已被明确接受，未来若确有瓶颈，可凭使用数据再行讨论。

**本流程不限于学生。** 教职工账号同样不设密码创建、同样处于待激活状态、同样凭 §4 的
一张单人凭证单激活。差别只在凭证单**之前**：学生的账号与用户名由名册导入生成（§3），
教职工账号由管理员在界面上手工创建、用户名由管理员指定。本文以学生为主线叙述，是因为
学生是批量场景，也是这套设计的动因；但"不存在任何初始密码"这条性质对每一个角色一律成立，
没有例外——有例外就等于没有。

## 3. 完整流程

```
① 管理员导入名册 CSV
        │  校验通过后，为每名新学生创建：
        │    · 学生名册行
        │    · 登录账号：8 位随机数字用户名，无密码哈希，状态 = 待激活
        ▼
② 账号存在，但在结构上无法登录
        │  没有密码哈希 ⇒ 任何密码都无法通过校验
        ▼
③ 管理员选择班级 → 生成凭证单 PDF（每名待激活学生一张）
        │  · 系统为每名学生签发一个一次性激活码
        │  · PDF 即时生成、直接下载，**不落盘保存**
        │  · 该班级此前未使用的激活码同时作废
        ▼
④ 凭证单打印、分发到学生手中（纸质）
        ▼
⑤ 学生激活（两条路径，同一个激活码）
        │  · 扫二维码 → 直接打开激活页，激活码已自动填入
        │  · 或手工访问站点首页 → 登录页「首次登录？使用激活码」→ 输入激活码
        │  学生在此页**自行设置密码**
        ▼
⑥ 账号状态变为"正常"，激活码作废
        ▼
⑦ 学生以「用户名 + 自设密码」正常登录
```

### 3.1 逾期未激活

激活码默认 **7 天**有效（可配置，并打印在凭证单上）。逾期仍未使用的账号进入**独立的
「已过期」状态**，而不是「已锁定」。

这两个状态刻意分开：「已锁定」意味着连续登录失败触发的暴力破解保护，「已过期」意味着
凭证单没送到学生手上。管理员看到这两种状态需要采取的行动完全不同，合并它们会让管理员
无从判断。

恢复方式：管理员重新签发即可，与首次签发是同一条路径。

### 3.2 凭证单遗失 / 忘记密码

**系统不提供任何自助找回入口。** 学生忘记密码时，必须以线下方式联系管理员——当面，
或通过纸质／邮件申请。登录页的「忘记密码？联系管理员」就是这条规则本身，不是占位文案。

管理员执行重置时发生的事与首次签发完全相同：清除原密码、账号回到待激活、签发新的一次性
激活码、生成一张新的凭证单。**重置不会产生新密码**，因此 §1 的承诺在重置路径上同样成立。

不提供自助找回的理由见 `08-mlps-level1-security-design-guide.md` §8.3：一个未经身份认证、
且能为调用者指名的任意账号签发凭证的接口，正是本设计要避免的攻击面；而要支持自助找回就
必须有可信的送达渠道，也就必须收集未成年人的手机号或邮箱，与 §4.3 的数据最小化直接冲突。

### 3.3 重新签发不影响已激活的学生

为某班级重新生成凭证单时，系统**只为仍未激活的学生**签发新码；已经自行设置过密码的学生
不受任何影响，其密码不变。丢了 5 张凭证单，不应当让另外 25 名一切正常的学生重新激活一次。

**但对仍未激活的学生，旧凭证单会立即失效。** 这是必须的：凭证单遗失正是重新签发的主要
原因，那张丢失的纸必须停止生效。管理端界面在执行前会明确提示这一后果。

## 4. 激活凭证单

### 4.1 样张

一名学生一张。下面是实际生成内容的排版示意（域名与姓名均为占位示例）：

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   首次登录？使用激活码                                        │
│   扫描二维码，或访问下方网址。                                 │
│                                        ┌───────────────┐    │
│   姓名                                  │ ███ ▄▄ █ ███ │    │
│   李* 红（Alex L.）                      │ █ ▄█▀▄▀█▄ █ │    │
│                                        │ ██▄ ▀█▀ ▄███ │    │
│   用户名                                │ ▀█▀▄█ ██▄▀█▀ │    │
│   48215577                             │ ███ ▄▀▄▄ ███ │    │
│                                        └───────────────┘    │
│   激活码                                     扫码激活         │
│   HKTZ4-9QP2M                                               │
│                                                             │
│   请核对地址栏显示的网址是                                     │
│   https://timebank.example.com                              │
│                                                             │
│   签发人：Teacher Wei Chen  签发时间：2026-09-17 08:15 UTC     │
│   有效期至：2026-09-24 08:15 UTC                             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

默认每页一张（A4）。管理员可在下载时选择每页两张以节省纸张，代价是需要裁切——
该选项只有 1 或 2 两个取值，不是任意数字。

### 4.2 每一项为什么在这里

| 内容 | 存在的理由 |
| :--- | :--- |
| **姓名** | 班主任要把三十张纸分发给三十个人，没有姓名就无法分发。这是纸上唯一用于"找到本人"的信息 |
| **用户名** | 登录时要输入的标识。学生此前从未见过它 |
| **二维码** | 扫码即打开激活页并自动填入激活码，学生不需要手动输入任何字符 |
| **激活码文本** | 二维码的兜底路径：没有摄像头、用教室公用电脑、家长手机扫不出来时仍可手工输入。二维码与文本承载的是**同一个**激活码，不是两套凭证 |
| **站点网址** | **这是防钓鱼锚点，不只是一个地址。** 本设计要求学生扫码后在打开的页面里输入凭证——这恰恰是钓鱼所利用的行为模式。纸面上印出真实域名，学生才有据可核对浏览器地址栏。**这句话只能印在纸上**：一个页面声称"请核对本页地址"是没有意义的，因为伪造的页面同样会这么说 |
| **签发溯源行** | 签发人、签发时间、有效截止时间。一旦发生外传，可据此定位批次与签发人 |

### 4.3 溯源行印在每一张上，不是每页一次

这一点容易被当作冗余而"优化"掉。**不可以。** 纸是会被裁开的——尤其在每页两张的排版下，
裁切正是预期操作。页级标记裁切后只会留在其中一张上，另一张就此失去全部溯源信息。

### 4.4 屏幕文案必须与纸面逐字一致

登录页的入口写作「首次登录？使用激活码」，激活页的标题与字段标签同样使用「激活码」。
纸上写"激活码"，屏幕上就不能写成"令牌"或"注册码"。

一个十二岁的学生拿着纸找屏幕上对应的位置，靠的就是字面匹配。这不是文案偏好，是可用性要求。

### 4.5 学生自设密码时的要求

学生在激活页设置的密码，与全系统其他任何设置密码的场景适用**同一套规则**（见
`08-mlps-level1-security-design-guide.md` §8.2）：不少于 12 位；小写、大写、数字、符号
四类中至少三类；不得是常见弱口令或包含弱口令词；不得包含系统名称或本人登录名；不得是
全同字符或连续规律串。

对一名十二岁的学生而言，这个要求并不轻。因此激活页**在输入过程中实时显示每一项要求是否
已满足**，而不是等到提交后再报错——一次只被告知一个问题，是让人放弃的最快方式。在全部
要求满足且两次输入一致之前，"激活并设置密码"按钮保持禁用；但未满足项始终可见，禁用状态
不会变成无从下手的僵局。

特别值得一提的一条是**不得包含本人登录名**：学生手里正拿着印有 8 位登录名的凭证单，把它
直接用作密码是最自然的反应，也正因如此必须拦住。

### 4.6 输入容错

激活码使用 **Crockford base32** 字符集，其字母表刻意剔除 I、L、O、U，从源头避免与 1、0 混淆。
激活页在学生输入时实时规范化：转为大写、自动去除分隔符、并将易混字符折回（`I`/`L` → `1`，
`O` → `0`）。因此把纸面看错、大小写输错，通常仍能成功。

激活码的第 10 位是**校验位**，可在浏览器本地校验。学生输错或颠倒一位字符时，页面立即提示
"这个码看起来不对"，而不是发一次请求再收到一句冰冷的"无效"。

## 5. 本流程成立所依赖的安全性质

| 性质 | 如何成立 |
| :--- | :--- |
| **凭证单送达之前，账号不可能被使用** | 未激活账号没有密码哈希，在结构上无法通过密码校验。这条保证由数据结构本身成立，不依赖流程纪律；认证前置检查同时要求「状态正常」**且**「存在密码哈希」，因此手工把状态改为正常也无济于事 |
| **系统中不存在密码明文** | 服务端从不生成密码，密码只在学生激活时由本人设定 |
| **激活码不以明文留存** | 仅存摘要并按摘要检索。其防护强度来自"单次使用 + 短有效期 + 此时账户尚无任何数据"，而非摘要算法本身——与保护密码的机制不同，不应等同看待 |
| **激活码不与用户名绑定** | 激活码本身即检索键，学生无需输入用户名即可兑换。猜中者也无法指定猜中谁 |
| **抵抗批量猜测** | 9 位数据字符约 4.5×10¹³ 种取值（第 10 位是校验位，不贡献强度）。真正起作用的是**全站级失败次数预算**：分布式猜测可绕过单 IP 限流，却绕不过全局预算 |
| **签发可追溯** | 每次签发写入审计日志：签发人、时间、班级、份数。**激活码本身绝不进入日志、审计记录或错误信息** |
