# 角色与权限设计

> 本文描述系统的角色模板、权限目录与数据范围模型，是数据导入（`12-DataImport.md`）
> 与数据导出（`13-DataExport.md`）两份设计的共同基础。
> 改动本文时请同步更新 `Design/english/11-RolesAndPermissions.md`。
> 相关文档：合规依据见 `08-mlps-level1-security-design-guide.md`；
> 角色早期调整的决策记录见 `Docs/optimization/07-RoleFinetune.md`。

---

## 1. 这份设计要回答的问题

"谁能做什么"在本系统里从来不是一个问题，而是两个：

1. **允许执行哪一类动作？**——能不能发起导出、能不能提交审核决定。
2. **动作能作用在哪些数据行上？**——能导出全校，还是只能导出自己带的年级。

把这两件事混成一个概念，是权限系统最常见的失败方式：一旦"教师导出"变成一个权限，
就再也无法表达"教师只能导出自己年级"，于是要么放宽到全校，要么干脆不给。

**本设计的核心选择：权限与数据范围是两个独立的轴，分别判定，缺一不可。**
一次请求必须同时通过两道检查——持有该动作的权限，且目标数据行落在该用户的范围内。

---

## 2. 三个概念

| 概念 | 回答的问题 | 存放位置 |
| :--- | :--- | :--- |
| **权限（permission）** | 允许执行哪一类动作 | `permission` 表，代码形如 `资源.动作` |
| **数据范围（data scope）** | 动作能作用在哪些数据行上 | `teacher_scope_assignment` 表，按资源类型分别绑定 |
| **角色（role）** | 一组权限的命名模板 | `role` / `role_permission` 表 |

角色只是权限的集合，本身不携带范围。同一个"教师"角色，绑定七年级的和绑定九年级的，
权限完全相同、可见数据完全不同。

**每位用户有且只有一个角色**（`07-RoleFinetune.md` §2.5）。多角色叠加会让"这个人到底
能看到什么"变成一道需要推演的题，而权限系统的价值恰恰在于它不需要被推演。

## 3. 四个角色模板

### 3.1 学生（`student`）

**是谁**：在校学生本人。账号由名册导入生成，凭激活凭证单首次登录（`10-StudentActivationFlow.md`）。

**能做什么**：提交服务记录与活动提案、报名项目、就审核结果发起申诉、查看本人的时间币
账户与达标进度、浏览项目与合作组织。

**刻意不能做什么**：看见任何其他学生的数据。学生的数据范围恒为"仅自己"，
不依赖任何绑定配置——这是结构性的，不是配置出来的。

**导入导出**：均无。学生不持有任何 `imports.*` 或 `exports.*` 权限。

### 3.2 教师（`teacher`）

**是谁**：承担审核与带班职责的教职工。账号由管理员手工创建，用户名由管理员指定。

**能做什么**：在**绑定年级范围内**审核服务记录与活动提案、查看学生目录与达标进度、
创建与发布项目、查看合作组织与服务类别词表（均为只读，后者含已停用项，见 §5a）、
导出本范围内的学生类报表。

**刻意不能做什么**：
- **不能导入任何数据**。名册与历史记录的批量写入是学生发展中心的职责，不是带班职责。
- **不能维护合作组织**（2026-09-22 改为管理员专属，此前教师持有 `organizations.manage`）。
  合作组织是共享词表：每个项目、每条服务记录都指向其中一条，改名或归档会改变别人的
  记录对自身的描述。教师保留 `organizations.read`——创建项目时要从列表中选主办方。
- 不能管理用户、角色与系统设置。
- 不能调整或冲正时间币账户。
- 不能导出"审核效率"报表——那是同侪绩效比较，见 §5.3。

**数据范围**：由 `teacher_scope_assignment` 按年级绑定。**未绑定任何年级的教师，
范围解析为"仅自己"**，其后果是看任何他人数据都得到 404 而非 403（B1.7 的不暴露存在性
约定）。这一点在排查时极易误判为"数据丢了"，因此凡新建教师账号，绑定年级是必做步骤。

### 3.3 学生发展中心管理员（`admin`，显示名 "SDC Admin"）

**是谁**：学生发展中心负责本系统业务运转的管理员。

**能做什么**：全校范围内的一切业务动作——名册导入、历史记录导入、凭证单签发与重置、
账户调整与冲正、规则版本发布、项目归档与取消、申诉处理、**全部导出类型**。
数据范围恒为"全部"，不依赖绑定。

**刻意不能做什么**：本角色是业务权威，不是技术权威。它不负责服务器、部署与数据库。

**这是唯一持有导入权限的角色。**

### 3.4 系统管理员（`sysadmin`，显示名 "System Admin"）

**是谁**：负责系统技术运维的管理员。

**能做什么**：用户与角色管理、系统设置、审计日志与登录日志、留存清理与账本对账等
技术性操作。

**刻意不能做什么**：
- **不能导入任何数据。**
- **不能导出任何学生数据。**

理由见 §6。

## 4. 权限目录

权限代码形如 `资源.动作`，按资源分组。现有分组：

`projects`、`eventProposals`、`applications`、`serviceRecords`、`reviews`、`cases`、
`students`、`progress`、`organizations`、`accounts`、`rules`、**`serviceCategories`**、
`reports`、**`exports`**、**`imports`**、`users`、`roles`、`auditLogs`、`securityLogs`、
`settings`、`lifecycle`、`directory`。

本次设计改动其中两个分组：`exports` 与 `imports`。
`serviceCategories` 是后来补上的一个分组，见 §5a。

## 5. `exports` 分组：一个导出类型一个权限

### 5.1 为什么不是一个 `exports.create`

若只有单一的 `exports.create`，持有它就意味着可以导出全部类型。教师一旦需要
导出学生名单，就会同时获得导出「审核效率」的能力——而后者是拿同事的审核数量与
通过率做横向比较的材料。在这个粒度上，只能在「给得太多」和「不给」之间二选一。

**因此每个导出类型拥有独立权限**，`exports.create` 退役：其权限行保留，
以便审计记录中「谁曾持有它」仍能解析，但它不再授予任何能力，也不可再被分配（§5.2）。

### 5.2 命名规则

```
exports.<导出类型键>
```

- **用导出类型的稳定键，不用显示标题。** 标题是 i18n 文案，会被改写；权限代码是
  数据库主键与审计日志里的字符串，不能跟着文案走。
- **不把范围编进名字。** 没有 `exports.studentList.ownGrade` 这种代码——范围是另一个轴，
  由 §7 决定。把它编进权限名，等于把两个轴重新混成一个。
- **不把格式编进名字。** 今天只有 CSV；未来若增加 XLSX，它是同一个导出的另一种呈现，
  不是另一项权限。
- **退役的权限保留行、标注退役，不删除也不复用**——与 `projects.close` 的处置一致。
  复用一个旧代码，会让历史审计日志的含义在某一天之后悄悄改变。

### 5.3 权限清单与角色分配

| 权限 | 导出类型 | 教师 | SDC 管理员 | 系统管理员 |
| :--- | :--- | :---: | :---: | :---: |
| `exports.studentList` | 学生名单 | ✓ | ✓ | — |
| `exports.serviceRecords` | 服务记录 | ✓ | ✓ | — |
| `exports.studentCompletion` | 学生达标情况 | ✓ | ✓ | — |
| `exports.studentParticipation` | 学生参与情况 | ✓ | ✓ | — |
| `exports.projects` | 项目报表 | ✓ | ✓ | — |
| `exports.reviewHistory` | 审核历史 | ✓（仅本人） | ✓（全部） | — |
| `exports.reviewEfficiency` | 审核效率 | — | ✓ | — |

`exports.reviewEfficiency` 不给教师，是因为它的每一行都是一位同事的审核量、
平均时长与通过率。这份数据在管理场景下是合理的，在同侪之间不是。

`exports.reviewHistory` 给教师，但**筛选器中的"审核人"固定为本人**——
权限允许导出这份报表，范围决定只能导出自己的那部分。这正是两个轴分开的价值。

## 5a. `serviceCategories` 分组：从 `rules.manage` 里拆出来

### 5a.1 为什么它不该寄居在 `rules.manage` 下

服务类别原本没有属于自己的权限，三个写接口一律检查 `rules.manage`——权限目录里
那一行的说明也直说了："创建或编辑规则草稿**与服务类别**"。一个权限，两件不相干的事。

这两件事不是一类。规则版本是带版本号、发布后不可变的政策对象，改动它会重算每一名
学生的达标状态；服务类别只是下拉框里的一个词。把它们绑在一个权限上，意味着学校无法
在"让某人整理类别列表"与"把决定谁能毕业的规则也交出去"之间划线——这正是 §5.1 在导出
那里拒绝过的那种粒度：只能在「给得太多」和「不给」之间二选一。

### 5a.2 两个权限，以及刻意不加的第三个

| 权限 | 覆盖范围 | 学生 | 教师 | SDC 管理员 | 系统管理员 |
| :--- | :--- | :---: | :---: | :---: | :---: |
| `serviceCategories.read` | 管理视图——**含已停用类别**的完整列表 | — | ✓ | ✓ | ✓ |
| `serviceCategories.manage` | 新建、重命名、停用、删除 | — | — | ✓ | ✓ |

**教师持有读权限。** 教师审核记录时整天都在和类别打交道；能看见完整的词表——包括
哪些已经停用，以及由此理解为什么一条旧记录里写着一个如今不再提供的类别——是在读
学校自己的字典，不是一项管理权力。

### 5a.3 普通字典读取不设权限

`GET /service-categories`（仅返回启用项，也就是各表单选择器背后的那份列表）
**维持"已登录即可"**。学生提交服务记录时必须能拿到它，而**一个每个角色都必须持有的
权限，实际上永远不会拒绝任何人**——它只是装饰，却附带一个故障模式：哪天漏给某个角色，
那个角色的表单就会静默失效。

真正受 `serviceCategories.read` 管的是 `?includeInactive=true`，即管理视图。
它比表单那份列表唯一多出来的东西，就是**哪些类别已被停用**。于是这个权限守住的是
一条真实的边界，而不是一条名义上的边界——线划在多出来的那部分信息上。

### 5a.4 `rules.manage` 只改说明，不改代码

`rules.manage` 的代码与"规则草稿"含义原样保留——权限代码是审计日志里的字符串，
必须始终保持原意（§9.3）。变的只是它的说明文字：后半句有了自己的归宿。

落库需要两半（§2.1 的两半规则）：新增权限与授予可以只靠 `R__seed_permissions_and_roles.sql`
（全是 `INSERT IGNORE`，内容变更时会在线上重跑），但**修正一条已存在行的说明只有
版本化迁移能做**——`INSERT IGNORE` 改不动既有行。因此 `V34__service_category_permissions.sql`
同时承担这两件事，全新库则由种子文件保证正确。

## 6. `imports` 分组：只有一个角色持有

导入保持按**工作流阶段**划分，而非按数据类型划分：

| 权限 | 含义 |
| :--- | :--- |
| `imports.create` | 上传文件并发起校验 |
| `imports.read` | 查看导入任务状态与错误报告 |
| `imports.commit` | 确认并提交入库 |

之所以按阶段而非类型切分：被管控的是"上传 → 校验 → 提交"这条流程本身（见
`12-DataImport.md` §3），而目前只有一个角色持有导入权限，再按类型细分不会带来
任何实际的区分度。若将来出现第二个需要导入的角色，再按类型拆分。

**三项权限仅 SDC 管理员持有。**

### 6.1 为什么系统管理员失去导入与导出

`Docs/optimization/07-RoleFinetune.md` §2.3 曾将 `admin` 与 `sysadmin` 的权限集合并为
完全一致（迁移 `V21`）。**本设计在导入与导出两处撤销该合并**，理由是这两类操作的
风险性质与系统管理职责无关：

- **导入**是批量写入学生数据，其中历史服务记录导入会直接影响时间币账本。这是学生发展
  中心的业务判断，不是运维动作。
- **导出**是批量取出学生数据——数据泄露风险最集中的一个动作。系统管理员需要的是让系统
  运转，不是取走学生名单。

代价是真实的：系统管理员排查导出故障时，无法自己跑一次导出复现。此代价已被接受——
排查可以通过日志与任务状态进行，而"技术管理员默认不持有学生数据出口"是一条更值得保留
的性质。

**唯一的例外不是例外。** 历史记录导入的时间窗到期后，只能由系统管理员在服务器控制台
上重新开启（`12-DataImport.md` §6.3）。这不构成对本条的削弱：那个工具重新开启的是
窗口，不向执行者授予 `imports.*`——**开关不是门**，重新开启之后能执行导入的仍然只有
学生发展中心管理员。

> **本次未做的事**：除导入导出外，`admin` 与 `sysadmin` 的其余权限仍保持一致。
> 两个角色是否应在用户管理、规则发布等方面进一步分开，是一个独立议题，
> 需要单独讨论，不在本设计范围内。

## 7. 数据范围模型

### 7.1 四种范围

`ScopeDescriptor` 是一个密封类型，调用方必须穷举处理，不存在"默认放行"的分支：

| 范围 | 含义 |
| :--- | :--- |
| `All` | 全部数据。SDC 管理员。 |
| `Grades` | 绑定年级内的学生。教师。 |
| `Classes` | 绑定班级内的学生。目前未使用，机制保留。 |
| `Self` | 仅本人。学生，以及**未绑定任何年级的教师**。 |

### 7.2 年级绑定是"现时"的，不随学年回溯

一位绑定九年级的教师，在导出**往年**数据时，看到的是**今天在九年级的那批学生**
在那一年的数据——而不是当年在九年级的那批学生。

这一点必须写明，因为它的表现初看反直觉：

> 十一年级教师导出 2024-2025 学年的报表，行是他现在带的十一年级学生，
> 而这些行的"年级"列会显示"九年级"——因为那一年他们确实在九年级。

两列指向不同时点，各自都对：

- **范围**回答"我今天有权看谁的数据"，是一项**现时的职责**；
- **年级列**回答"报表所属的那一年，这名学生在哪个年级"，是一项**历史事实**。

### 7.2.1 并非每个资源都按学生的现时年级过滤

上面那句"看到的是今天在九年级的那批学生"只对**以学生为主体**的资源成立。

年级被冗余写在六张表上，而范围过滤读的是**每张表自己的那一列**
（`14-AnnualRollover.md` §3.4）。于是同一个教师，在两类界面上看到的范围并不相同：

| 主体 | 按什么过滤 | 教师看到的是 |
| :--- | :--- | :--- |
| 学生、账户 | 学生／账户的**现时**年级 | 我今天带的这批学生 |
| 服务记录、申诉、活动提案 | 记录自身的**年级快照** | 在我年级内发生过的事 |

差异在升年级之后立刻显现：一名刚从八年级升上来的学生，其八年级时期的服务记录带的
是八年级快照，**九年级教师看不到**；反过来，一名升去十年级的学生，其九年级时期的
记录仍带九年级快照，九年级教师**仍然看得到**。

两者各有其道理：审核队列按快照过滤是对的——你审的是发生在你年级里的事；
而"我这批学生现在怎么样"显然应当按学生过滤。

**因此导出统一按学生取范围**（`13-DataExport.md` §4.4）：一份导出是一张关于学生的
报表，行由学生决定，该学生的数据不因当年记录挂在哪个年级而被裁掉。审核队列等
以记录为主体的操作界面维持按快照过滤，不受此影响。

**学段边界同时限定了能回看多远。** 八年级升九年级是毕业加重新入学
（`14-AnnualRollover.md` §2.1），九年级学生在本系统中是一条全新的学生记录。
因此一位九年级教师把学年选到该生入学之前，得到的是**零行**——那一年这个人
在系统里以另一条记录存在，且不在他的范围内。这是正确结果，不是数据缺失。

年级列的推导规则见 `13-DataExport.md` §5。

### 7.3 范围为 `Self` 的教师导出结果为空

未绑定年级的教师持有导出权限却导不出任何行。这是正确行为，不是故障——但它与
"绑定配置错误"在界面上无法区分，因此导出结果为空时，界面需明确提示
"你尚未被分配任何年级"，而不是显示一个空文件。

## 9. 新增权限时的规则

1. **先确定它是权限还是范围。** "只能看自己年级"不是权限，是范围；
   "能不能导出"才是权限。
2. **新增导出类型必须同时新增权限**，并在本文 §5.3 的表中登记角色分配。
   遗漏会导致该导出对所有人不可见（无人持有），或被并入某个已有权限（粒度倒退）。
3. **权限代码一经使用不得更名、不得复用。** 审计日志里留存的是代码字符串。
4. **新权限默认不授予任何角色**，再逐一决定。反过来做——先给所有管理角色再收回——
   意味着在收回之前它一直是放行的。

## 10. 刻意不做的事

- **没有字段级权限。** 谁能看到哪一列，由导出类型的定义决定，不由权限系统逐列判定。
- **没有临时授权 / 代理。** 不存在"把我的权限借给同事三天"的机制。
- **没有否定式权限。** 权限只做加法；不存在"有 A 但排除 B"的减法规则，
  因为两条减法规则叠加后的结果无法靠阅读得出。
- **不按学段（初中／高中）分角色。** 学段差异体现在规则版本的达标要求上，
  不体现在权限上。
