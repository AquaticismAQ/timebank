# 时间银行部署分级：学校项目负责人决策指南

> **预算规划指南，不是供应商报价。** 编制于 2026-09-01，供决定如何启动时间银行系统的学校使用。金额为人民币月度及年度规划区间，未含税费、促销、教育折扣、域名/ICP/WAF 费用、实施人力及数据迁移项目费用。批准采购前，应向所选区域的阿里云获取注明日期的报价。

> **必要部署材料——应在选择层级前准备。**
>
> 1. **域名和 DNS 变更：** 学校网管应选择经批准的学校子域名，并将其 DNS 记录指向新服务器或负载均衡器的公网地址。可使用学校自有地址，例如 `tb.example.com` 或 `timebank.example.com`；实际学校域名须由校方在上线时配置，不得写入本仓库。DNS 变更完成后，才能签发 TLS 证书并测试 HTTPS。
> 2. **学生花名册导入样本：** 学校须按约定导入格式提供一份*虚构或已完全匿名化*的花名册样本，用于验证导入流程。真实学生花名册属于高度敏感个人信息，必须由获得授权的学校工作人员准备和导入，不能由开发或维护人员导入。学校应验证生成的账户；如发现字段映射问题，只能用不含身份信息的示例反馈。
> 3. **历史纸质账册样本：** 学校须提供既有纸质账户账册的脱敏样页，并说明每一列及例外情况。这些样本用于完成和验证历史账册导入实现，使其符合学校既有记录。不得向开发人员发送原件或包含非必要学生身份信息的文件。
> 4. **如需邮件通知，须采购邮件转发服务：** 如学校希望系统发送邮件通知，须采购并配置获批准的事务邮件服务或 SMTP 转发服务。服务商须支持学校域名、发件人认证、送达监测和退信处理。这是独立于应用服务器的服务；各档成本中仅预留小额额度，最终须以供应商报价为准。

## 1. 一页决策摘要

时间银行处理学生个人信息、服务记录、审计历史和证据文件。因此，系统选型应以学校可接受的中断时长和可能需要恢复的数据量为依据，而不只是比较最低云服务账单。

| 层级 | 适用场景 | 预计月度成本 | 预计年度成本 | 通俗建议 |
| --- | --- | ---: | ---: | --- |
| **1. 低成本试运行** | 单校有限试点、UAT、演示或早期受控上线 | **¥172.01**（按年付价格折算） | **¥2,064.12** | 仅在可接受一天或更长服务中断、且学校指定了能够恢复服务器的技术负责人时选择。 |
| **2. 托管数据库标准方案** | 单校常规的首次正式部署 | **¥1,500–¥1,800** | **¥18,000–¥21,600** | **多数学校的推荐起点。** 保留一台应用服务器，但将 MySQL 迁至阿里云 RDS，降低数据库运维风险。 |
| **3. 具备容灾能力的高可靠方案** | 多个年级每天依赖系统、对中断或数据丢失容忍度较低的场景 | **¥3,800–¥4,800** | **¥45,600–¥57,600** | 当业务连续性已是学校管理要求，且预算能覆盖运维演练与云服务时选择。 |

第二、三档的区间特意预留了 RDS 价格、证据下载流量、备份增长量和区域差异的浮动空间。第一档改按本指南所列的最低年度采购价格计算；其金额未含公网带宽、域名/ICP/WAF、邮件、备份超额、OSS 请求及下载流量等按实际用量或另行采购的费用。付费订阅本身并不能保证服务可用：必须实际测试备份恢复和故障切换。

## 2. 每个层级都包含什么

三个层级都包括 Web 应用、HTTPS 访问、私有数据库访问、私有对象存储桶中的证据存储、常规邮件通知、基础容量监控和备份。证据文件应存入对象存储，并通过有时限、经授权的链接访问；不应长期保留在应用服务器的本地磁盘中。

估算以一所学校、约 3,000 名学生、300 个教职工账号和 300 名峰值并发用户的设计目标为前提。该目标仍需通过接近真实生产情况的压测验证；本指南用于资金决策，并不构成容量已获证明的结论。

## 3. 第一档——低成本试运行

### 建议配置

- 一台 `ecs.e-c1m1.large`（2 vCPU / 2 GiB）ECS，运行应用程序和 Nginx；这是截图所示的最低价 ECS，仅适用于小范围试运行。
- 一台 RDS MySQL 基础系列实例（2 核 / 4 GB、50 GB），承载业务数据库；不在 ECS 上自主管理 MySQL。
- 100 GB OSS 标准本地冗余存储用于证据文件；数据库与对象存储均使用 KMS 默认密钥提供的服务端加密。
- KMS 使用免费默认服务密钥/主密钥，不购买软件密钥管理实例；另按需要采购备份副本和事务通知邮件服务。
- 一个公网入口；没有备用应用服务器，也没有数据库备用节点。

### 预算构成

| 主要成本项 | 月度规划额度 | 说明 |
| --- | ---: | --- |
| ECS `ecs.e-c1m1.large`（2 vCPU / 2 GiB） | ¥19.86 | 截图所示优惠月价；按同一价格连续 12 个月计算为 ¥238.32/年。 |
| RDS MySQL 基础系列（2 核 / 4 GB、50 GB） | ¥143.90（年付折算） | 截图所示年付 ¥1,726.80；月度数字仅用于横向比较，并非月付报价。 |
| OSS 标准本地冗余存储（100 GB） | ¥8.25（年付折算） | 截图所示年付 ¥99.00；月度数字仅用于横向比较，并非月付报价。 |
| KMS 默认服务密钥/主密钥 | ¥0 | RDS、OSS 等云产品的服务端加密可使用免费默认密钥；不包含付费软件 KMS 实例。 |
| **总计** | **¥172.01**（年付折算） | **¥2,064.12/年**（ECS ¥238.32 + RDS ¥1,726.80 + OSS ¥99.00）。 |

### 使用效果

正常使用时，门户可以提供与其他层级相同的核心功能：学生提交记录和证据，教职工审核并审计。它是初期采购和运维最容易理解的方案。

由于此层级采用 2 vCPU / 2 GiB ECS，且 RDS 也是最低截图规格，它只是受控试运行配置，不是“可支持 300 人并发”的容量承诺。应保持初期试运行规模很小，将批量导入和报表安排在教学时间之外，并在实际压测后再扩容，不能仅凭此预算数字判断容量。

### 优势、限制与风险

| 优势 | 限制与风险 |
| --- | --- |
| 经常性成本最低，最容易理解。 | 单台服务器故障、磁盘故障、升级失败或 MySQL 问题都可能使整个系统停止服务。 |
| 适合在扩大上线前了解真实使用模式。 | 恢复依赖可用备份和能够执行恢复的人；中断可能持续数小时甚至更久。 |
| 采用托管 RDS、私有 OSS 与 KMS 默认密钥，满足本系统生产环境的数据库、证据存储和服务端加密基础设施前提。 | 100 GB OSS 只是初始证据容量；下载流量、请求、备份和超额存储另行计费，不能把年度包价误解为全部运行成本。 |

**决策边界：** 此层级只能作为有明确期限的试运行。不能因为试运行顺利，就在未重新评估风险和升级的情况下，将其自然延续为全校关键服务。

## 4. 第二档——托管数据库标准方案（推荐）

### 建议配置

- 一台应用服务器，初期为 4–8 vCPU / 16 GiB，约 100 GB SSD。
- 单可用区的阿里云 RDS for MySQL，初期为 4 vCPU / 16 GiB 和 200 GB 数据库存储。托管数据库替代学校自主管理 MySQL 的日常工作；高可用 RDS 和跨可用区应用部署属于第三档。
- 私有对象存储用于证据、托管数据库备份/按时间点恢复容量、邮件服务和基础监控。

### 预算构成

| 主要成本项 | 月度规划额度 | 说明 |
| --- | ---: | --- |
| 应用 ECS、100 GB SSD 和 5 Mbps 固定带宽 | ¥825 | ¥600 计算资源 + 约 ¥100 SSD + ¥125 带宽。 |
| RDS MySQL 基础版，4 vCPU / 16 GiB，200 GB 存储 | ¥550 | ¥480 实例 + ¥70 高性能云盘存储。 |
| 对象存储、备份超额、邮件和基础监控额度 | ¥125–¥425 | 证据增长和备份保留政策是主要变量。 |
| **总计** | **¥1,500–¥1,800** | **每年 ¥18,000–¥21,600**（取整）。 |

### 使用效果

普通用户在功能上不会感到与第一档有区别。实际改善在于：云服务商负责数据库软件和备份设施，学校日常 MySQL 运维负担更低。

### 优势、限制与风险

| 优势 | 限制与风险 |
| --- | --- |
| 数据库运维负担较低，云服务商的支持边界更清晰。 | 应用服务器和单可用区数据库仍都是单点；服务器或可用区故障仍可能造成中断。 |
| 更适合作为备份保留和按时间点恢复的基础。 | 托管 RDS 不能替代恢复测试、访问控制或审慎的应用/数据库变更。 |
| 对单校而言，在成本与运维简化之间较为平衡。 | 没有自动跨可用区数据库故障切换；连续性要求更高时应选择第三档。 |

## 5. 第三档——具备容灾能力的高可靠方案

### 建议配置

- 两台应用服务器分布在不同可用区，由负载均衡器承接流量。一台应用服务器故障后，另一台仍可继续提供门户服务。
- 跨可用区的阿里云 RDS for MySQL 高可用版，具备自动故障切换和按时间点恢复能力。
- 私有对象存储用于证据，配置生命周期管理；在数据驻留政策允许的前提下建立跨可用区或跨区域备份副本，并持续监测备份验证结果。
- 集中监控和告警、书面化的事件联系人，以及定期恢复/故障切换演练。

### 预算构成

| 主要成本项 | 月度规划额度 | 说明 |
| --- | ---: | --- |
| 两台应用 ECS、磁盘、5 Mbps 带宽和负载均衡额度 | ¥1,625–¥1,825 | 两台均为 4 vCPU / 16 GiB、各配 100 GB SSD；区间包含负载均衡额度。 |
| RDS MySQL 高可用版，4 vCPU / 16 GiB，200 GB 存储，以及备份/按时间点恢复额度 | ¥1,560–¥1,860 | ¥1,360 实例 + ¥100 存储，另加备份保留额度。 |
| 证据存储、受保护副本、邮件、监控和恢复验证额度 | ¥615–¥1,115 | 包含 700 GB 主证据容量、受保护副本、下载/复制额度和持续检查。 |
| **总计** | **¥3,800–¥4,800** | **每年 ¥45,600–¥57,600**（取整）。 |

### 使用效果

与第一、二档相比，大多数故障不会造成中断，或中断明显更短。遇到严重基础设施故障时，学校可能只会看到短暂维护提示，服务切换或恢复后即可继续使用，而不是等待从备份重建一台新服务器。

### 优势、限制与风险

| 优势 | 限制与风险 |
| --- | --- |
| 消除了单台应用服务器故障点，并为数据库提供托管备用节点。 | 月度成本明显更高，并且仍需要持续的技术责任人。 |
| 对日常学校业务和证据连续性提供最强的实际保护。 | 它不是绝对保证：有缺陷的发布、错误删除、账号被盗用或区域性事件仍可能影响服务。 |
| 定期恢复演练使备份从“假设存在”变为“已经验证”。 | 跨区域容灾必须遵守学校的数据驻留和个人信息处理审批要求，不能随意启用。 |

## 6. 预算无法彻底消除的风险

| 风险 | 学校应采取的行动 |
| --- | --- |
| 证据量超过规划额度 | 每月检查对象存储用量；通过经批准的生命周期和保留规则处理，不得临时随意删除文件。 |
| 账号被滥用，或教职工做出错误决定 | 保持角色权限、审计日志复核，以及既有的不可覆盖审核流程。 |
| 备份存在但无法恢复 | 定期恢复到隔离的临时环境，并记录结果。 |
| 软件更新造成中断 | 生产变更前使用预发布环境并准备回滚方案。 |
| 假定具备容灾能力但从未演练 | 第三档至少每年进行一次书面化故障切换演练，并在重大架构变更后再次演练。 |

## 7. 审批清单和推荐路径

对多数学校，建议批准**第二档**作为首个正常生产年度的方案，并在一个学期的实际测量使用后进行书面复核。只有在范围被明确限定为受控试运行、且管理层接受其中断和恢复风险时，才从第一档开始。当学校的日常业务依赖该系统，且已认定较长中断或本可避免的数据恢复事件不可接受时，应批准第三档。

签订合同前，项目负责人应确认：

1. 所选云服务区域、数据驻留立场及所需的校内/法律审批。
2. 针对计算资源、RDS 版本、存储、带宽和备份保留期限的最新供应商报价。
3. 事件处理的指定技术负责人和升级联系人。
4. 可接受的最长中断时间和最大数据恢复缺口，并以小时表示。
5. 性能压测、备份恢复以及第三档故障切换演练的预算和日程。
