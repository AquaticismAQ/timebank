# 测试服务器容量估算

> 本文为工程估算，不是经过实测的容量保证。编制日期为 2026-08-26，目标为一台专用测试服务器：8 核 CPU、8 GB 内存、60 GB 存储。目前尚未执行要求的 300 并发用户压力测试。

## 1. 结论摘要

| 容量维度 | 建议规划值 | 有条件的上限目标 |
|---|---:|---:|
| 功能测试/UAT 注册用户 | 5,000 名学生 + 500 名教职员工 | 证据文件稀疏或使用合成数据时可行 |
| 本地保存一年代表性证据的活跃用户 | 1,000–1,500 名学生 + 100–150 名教职员工 | 仅在文件大小符合设计平均值且严格控制磁盘时，可接近 1,875 学生年 |
| 同时在线用户 | 100–200 | 调优并通过压力测试后为 250–300 |
| 持续请求速率 | 40–60 请求/秒 | 不能替代基于真实工作负载的验证 |
| 短时突发请求速率 | 100–150 请求/秒 | 尚未验证；取决于接口组合和数据库竞争 |
| 同时上传证据 | 10–20 | 更高数值需实测磁盘、网络和 JVM 余量 |

该服务器适合功能测试、集成测试、演示和受控试点。8 核 CPU 足以承担预期应用负载；8 GB 内存仅在 JVM 与 MySQL 谨慎共享内存的情况下可用。主要硬性限制是 60 GB 磁盘：按架构设计数据量，它无法保存全校、多年的证据资料。

## 2. 范围与假设

本估算基于以下假设：

- 性能测试期间，该主机专供 TimeBank 使用；
- Nginx、Spring Boot 后端、MySQL、日志以及本地证据存储共用同一主机；
- React 前端以静态资源方式提供，稳定运行时的 CPU 占用可忽略；
- 常规流量包括登录、分页列表、详情查看、报名/审核流程、账户查询以及未读通知轮询；
- 导入、导出、报表、文件上传和后台任务比常规浏览更重；
- HTTPS 终止和网络带宽充足；以及
- 容量测试期间不运行无关的构建、备份或分析工作负载。

正式架构目标为 5,000 名学生、500 名教职员工、300 峰值并发用户、持续 60 请求/秒和突发 200 请求/秒。参见[后端设计 §3.1](../backend/Design.md#31-design-target-per-deployment--per-school)。这些是系统设计目标，并不表示这台一体化主机已经达到这些指标。

## 3. 决定容量的架构因素

### 3.1 应用与数据库执行

Spring Boot 使用虚拟线程，可降低等待线程的成本，但不会创造数据库容量。需要访问 MySQL 的请求仍会竞争 HikariCP 连接。当前默认连接池大小为 5，这是针对原有共享测试主机的保守设置。对于这台 8 GB 主机，连接池从 15 开始较合理；只有在测量 MySQL 内存、锁竞争和响应延迟后，才应提高到 20。

应用主要执行事务型 CRUD 和分页查询，对 CPU 容量较有利；但仪表盘、宽范围筛选、导出以及索引不佳的查询可能消耗远高于平均水平的数据库时间。

### 3.2 数据库大小与访问模式

后端设计估算关系型数据稳定状态为 10–20 GB。只有在证据文件存放于其他位置，并控制日志和 binlog 时，这一规模才适合本机磁盘。全部数据无法同时放入内存，因此索引质量和 MySQL 缓冲池工作集比注册账号总数更重要。

注册账号本身成本较低。活动历史、服务记录、审计日志、通知行和账户流水才决定数据库增长与查询压力。

### 3.3 后台任务

当前后台任务执行器有 2 个工作线程，队列长度为 50。在此主机上保留两个工作线程较合理，因为导入和报表生成会与交互流量竞争。除非测试场景明确要求评估这种相互干扰，否则不应在大型导入或导出期间判断正常浏览容量。

### 3.4 证据存储

证据当前通过本地存储适配器保存，单个上传文件允许最大 20 MB。架构设计估算一所 5,000 名学生的学校每年产生 200,000 个证据文件，约七年累计 550–700 GB。

推导出的年度规划值：

```text
550–700 GB / 7 年 = 每学年约 79–100 GB
79–100 GB / 5,000 名学生 = 每学生年约 16–20 MB
```

平均值会掩盖突发风险。即使年度平均值看似安全，一个班级同时上传多张照片也可能对网络、临时磁盘空间、JVM 请求处理和存储 I/O 造成压力。

## 4. 容量估算

### 4.1 注册账号与业务数据行

| 场景 | 预计可支持人数 | 理由 |
|---|---:|---|
| 稀疏的功能测试/UAT 数据 | 5,000 名学生 + 500 名教职员工 | 账号和普通关系型数据行不是主要限制 |
| 本地保存代表性的一年活动与证据 | 1,000–1,500 名学生 + 100–150 名教职员工 | 为数据库增长、日志、临时文件和安全余量保留实际可用空间 |
| 多年全校历史 | 不建议使用 60 GB 磁盘 | 仅证据数据就会大幅超过磁盘预算 |

因此，这台主机可以初始化并运行设计规模的 5,500 个账号，但这不等于它能够保存符合生产数据形态的证据档案。

### 4.2 同时访问与请求速率

| 负载级别 | 评估 |
|---|---|
| 100 名同时在线用户 | 普通混合导航的宽裕目标 |
| 200 名同时在线用户 | 正式压力验证前的建议规划上限 |
| 250–300 名同时在线用户 | 经调优后合理的测试目标，但必须用符合生产形态的场景证明 |
| 超过 300 名同时在线用户 | 超出当前单校设计目标，不在本估算支持范围内 |

“在线”不等于“同一时刻正在执行请求”。例如，300 名用户每 30 秒轮询一次未读数，仅轮询就会产生约 10 请求/秒，尚未计入页面导航和写操作。

真实混合工作负载下，预计可持续范围为 40–60 请求/秒。系统可能吸收 100–150 请求/秒的短时突发，但这不是保证。在实测前，不应宣称该主机达到正式设计的 200 请求/秒突发目标。

证据提交是独立的约束。在以代表性文件大小完成测试前，计划同时上传数量应限制在约 10–20。可以允许 500 名学生在 30 分钟内完成提交，但不应让他们在同一秒全部上传。

### 4.3 本地存储容量

60 GB 磁盘可按以下方式合理规划：

| 用途 | 规划分配 |
|---|---:|
| 操作系统、软件包、JDK、应用发布版本 | 8–12 GB |
| MySQL 数据、索引、binlog 和临时空间 | 初始 6–10 GB |
| 应用/Nginx 日志、导出、上传临时文件、运行余量 | 4–6 GB |
| 必须保留的可用空间 | 10–12 GB |
| 剩余证据预算 | 约 20–30 GB |

按架构平均值每学生年 16–20 MB 计算，20–30 GB 约等于 1,000–1,875 学生年。建议范围更保守，即一年内 1,000–1,500 名活跃学生，因为平均值无法覆盖大尺寸照片、重试、导出、binlog 峰值或操作失误。

如果实际平均每个证据文件为 1 MB，每名学生每年约产生 40 个文件，则每学生年约占用 40 MB。同样的证据预算只能支持约 500–750 学生年。

### 4.4 外部对象存储的影响

将证据迁移到外部对象存储，可以消除最主要的磁盘增长约束。此后，在该主机上以 5,000 名学生加 500 名教职员工进行功能和性能测试是合理的，但 300 并发用户仍需通过压力测试验证。

外部对象存储不会消除：

- MySQL 与 JVM 的内存竞争；
- 数据库连接池限制；
- 上传带宽和请求大小压力；
- 后台任务干扰；以及
- 对证据生命周期、授权和审计控制的需求。

## 5. 8 GB 主机建议配置

| 组件 | 起始配置 | 说明 |
|---|---|---|
| Spring Boot JVM | `-Xms1g -Xmx2g` | 验证原生内存、线程栈和文件上传行为 |
| HikariCP | `TIMEBANK_DB_POOL_SIZE=15` | 仅在实测后考虑提高到 20 |
| MySQL InnoDB 缓冲池 | 约 3 GB | 仅在操作系统和 JVM 余量健康时提高到 3.5–4 GB |
| 后台执行器 | 2 个工作线程，队列 50 | 初始保留当前设置 |
| 操作系统/Nginx/原生内存/页缓存预留 | 约 2 GB | 持续测试期间避免发生 swap |
| 磁盘可用空间告警 | 低于 20% 前告警 | 低于 10% 前停止证据增长 |

运行控制：

- 轮转并限制应用、Nginx 和 MySQL 日志；
- 监控 MySQL binlog 保留周期和临时磁盘用量；
- 性能测试期间不运行 Maven 构建、前端构建、备份或大型软件包升级；
- 将批量导入和大型报表安排在交互负载测试以外；
- 按学校、按月监控证据大小；以及
- 将证据清理设计为经过授权、可审计的生命周期操作，而不是临时直接删除文件。

## 6. 提高上限前必须完成的验证

在对外宣称支持 250–300 并发用户前，应执行符合生产数据形态的压力测试：

1. 初始化约 5,000 名学生、500 名教职员工，以及真实规模的项目、报名、服务记录、账户流水、通知和审计日志。
2. 分别以 100、200、300 并发用户运行混合用户路径。
3. 单独测试“500 名学生在 30 分钟内提交”的必要场景，并使用代表性证据文件大小。
4. 在独立的干扰测试中并行运行大型导入。
5. 记录 p50/p95/p99 延迟、错误率、CPU、JVM 堆与 GC、swap、Hikari 活跃/等待连接、MySQL 缓冲池与慢查询指标、磁盘延迟/可用空间以及后台队列深度。

验收应继续采用后端设计目标：列表/详情接口 p95 低于 300 毫秒，仪表盘 p95 低于 1 秒，同时不得出现持续的连接池排队、swap 抖动、后台队列溢出或磁盘耗尽。

## 7. 最终建议

| 运行模式 | 人数 | 同时访问 | 证据策略 |
|---|---:|---:|---|
| 全账号 UAT | 5,000 名学生 + 500 名教职员工 | 规划 100–200；测试 300 | 稀疏或合成的本地证据 |
| 真实的一年本地试点 | 1,000–1,500 名学生 + 100–150 名教职员工 | 100–200 | 本地保存代表性证据 |
| 全校性能测试 | 5,000 名学生 + 500 名教职员工 | 调优后以 300 为目标 | 强烈建议使用外部对象存储 |

简言之：CPU 足够，内存可用但共享余量较紧，存储是限制资源。可将此服务器用于受控试点或全账号 UAT；在把它视为符合生产形态的全校证据部署之前，应增加对象存储或显著扩充磁盘。
