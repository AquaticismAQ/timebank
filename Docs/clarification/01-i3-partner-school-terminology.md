# 关于 I3.7 及后续计划中“合作学校”阻塞判断的澄清与修订建议

## 1. 结论

`Docs/implementation/13-Integration-I3-Acceptance.md` 将 I3.8-I3.12 统一描述为“需要真实合作学校（real partner school）”并因此全部阻塞，这一判断混淆了三类不同概念：

1. **系统部署学校/使用学校**：运行时间银行、配置学生与教师、组织 UAT 并决定上线的学校。
2. **活动提案中的合作组织**：学生可以从历史合作组织中选择已有 `organizationId`，也可以输入尚未收录的组织名称，由后端创建组织记录、自动生成新的 `organizationId`，再连同联系人信息关联到提案。
3. **外部合作学校（partner school）**：当前前端设计和 API 契约均未将其定义为学生发起活动或完成 I3 验收的前置条件。

因此，I3 不应以“尚无 partner school”为统括性阻塞理由。真正依赖实际部署机构、真实历史数据或正式上线日期的部分，应逐项写明尚缺的具体输入；其余工作应继续使用测试账号、代表性测试数据和既有真实技术栈完成。

## 2. 前端设计 5.3 的正确含义

`Docs/frontend/Design_CN.md` §5.3“发起志愿活动”规定，学生通过六步表单向**本校**提交活动提案。第 3 步“组织安排”包含：

- 学生发起人；
- 共同组织者；
- 拟邀请指导教师；
- 合作组织；
- 联系人。

这些是活动提案表单必须承载、保存并提交审批的组织信息。这里的“合作组织”与 API 契约 §3.2 的 `organizationId`、`externalContact` 对应，契约使用的英文也是 **partner organization**，不是 **partner school**。

合作组织采用以下双路径录入规则：

1. **选择历史合作组织**：学生通过可搜索选择控件从 `GET /organizations` 返回的历史记录中选择，提案直接保存已有 `organizationId`。
2. **新增合作组织**：若历史记录中不存在，学生输入组织名称和本次活动联系人信息；后端创建新的组织记录，自动生成 `organizationId`，并将该 ID 关联到提案。

这里的“自增”应理解为**新增记录时由服务端自动生成标识**，而不是允许前端计算、指定或解析连续数字 ID。项目既有约定要求 ID 是不透明的服务端生成字符串；当前 `OrganizationServiceImpl.create()` 也已通过 `OpaqueIds.generate("org")` 生成组织 ID。新建路径应继续遵守这一约定。

前端提交时应明确二选一：提供已有 `organizationId`，或提供新组织名称；不应要求学生为了提交活动提案而预先获得 `organizations.manage` 权限。推荐由提案创建/更新事务负责解析该二选一输入：选择已有记录时校验其存在且可用，输入新名称时完成必要的名称去重检查、创建组织、生成 ID、关联提案和审计记录。这样不会把组织管理权限直接扩大给学生，也不会产生“先建组织成功、后建提案失败”的孤立记录。

该流程的责任边界是：

- 学生是提案发起人，并可成为批准后项目的学生负责人；
- 指导教师或管理员仍是正式项目责任人；
- 提案批准时，后端在同一事务中生成正式项目草稿并回填 `approvedProjectId`；
- 具有 `projects.publish` 权限的教师或管理员确认后，正式项目才可发布；
- 合作组织及联系人是提案内容，不是要求另有一所学校参与审批、UAT 或上线。

即使某项活动由校内组织实施，也应在表单和数据模型中明确记录其组织安排，而不是因为没有“合作学校”就阻止提案流程。是否允许某一活动声明“无外部合作组织”，应由表单规则和审批规则明确处理；这也不等于要求存在合作学校。

## 3. I3.7 的修订

I3.7 是对 `APIContract_CN.md` §11 十二个场景的系统验收。它验证的是状态机、权限、事务、幂等、本地化和真实前后端联通，不要求真实合作学校。

`13-Integration-I3-Acceptance.md` 已在后续段落中承认 I3.7 曾被错误归入 I3.8-I3.12，但计划仍应进一步修订：

1. 从所有“I3.7-I3.12 均依赖 partner school”的历史性概括中移除 I3.7，避免状态文档继续传播旧结论。
2. 立即使用一次性学生、教师、管理员账号完成剩余场景 #1、#4、#12，不再等待外部机构。
3. 场景 #1 不应只验证状态变化和项目生成；还应验证 §5.3 的组织安排完整进入真实请求、修订版本、审批详情和生成后的项目：
   - 发起学生身份由当前登录学生确定并保存；
   - 共同组织者被保存为真实学生 ID 列表；
   - 拟邀请指导教师被保存为有效教师 ID；
   - 选择历史合作组织时，已有 `organizationId` 被正确保存；
   - 输入新组织名称时，后端自动创建组织、生成新的不透明 `organizationId` 并关联提案；
   - 联系人信息被保存并在审批详情中可见；
   - 批准生成项目时，学生负责人、指导教师和合作组织被正确继承。
4. 场景 #12 的双语、移动端和桌面端检查应覆盖完整提案表单，而不只是列表页或审批按钮。

## 4. 当前实现中应纳入 I3.7 的提案缺口

现有代码表明，“组织安排”虽然出现在页面上，但真实 API 路径尚未完全表达设计语义：

- `frontend/src/app/components/student/EventProposals.tsx` 把共同组织者显示为自由文本且标记为非必填；
- `frontend/src/app/api/client.ts` 在真实创建/更新请求中始终发送 `coOrganizerStudentIds: []`，页面输入的共同组织者没有传给后端；
- 指导教师目前是文本输入，但请求字段是 `proposedSupervisorId`，应改为可解析并提交有效教师 ID 的选择控件或搜索选择控件；
- 合作组织目前只有一个文本输入，却直接映射到 `organizationId`，既不能可靠选择历史组织，也不能表达“输入新名称并创建组织”的路径；前端需要可搜索的历史组织选择和“新增组织”入口；
- 当前 API 契约的提案请求只定义 `organizationId`，未定义新组织名称输入；`POST /organizations` 又要求 `organizations.manage`，学生无法按设计自行完成新组织创建。契约应增加提案专用的互斥输入，例如已有 `organizationId` 或 `newOrganizationName`（以及必要的联系人字段），并由后端在提案事务内完成创建和关联；
- 前端把合作组织标记为非必填；后端 `CreateProposalRequest` 对 `organizationId` 与 `externalContact` 也未施加必填校验，与本次对 §5.3“必要内容”的澄清不一致；
- I3.7 场景 #1 目前的已有证明主要覆盖“提交→批准→生成项目”，不足以证明上述组织信息被完整保存和继承。

这些是提案数据完整性和验收覆盖问题，不是“缺少合作学校”造成的基础设施阻塞。应先修正字段采集、ID 映射、提交校验和端到端断言，再关闭 I3.7 场景 #1。

## 5. I3.8-I3.12 的逐项重分类

| 项目 | 原计划判断 | 修订后的判断 | 现在可执行的工作 | 真正需要等待的输入 |
| --- | --- | --- | --- | --- |
| I3.8 历史台账导入演练 | 需要 partner school，全部阻塞 | 不依赖合作学校；机制验收现在可做，真实对账依赖部署学校的历史台账 | 用覆盖正常行、重复行、非法行、修正、确认、批次回滚的代表性数据完成全流程；完成 API 场景 #7 | 若目标学校确有历史台账，再用匿名副本完成最终纸面余额核对；若无历史数据，应明确记为“不适用”，而非“阻塞” |
| I3.9 真实用户 UAT | 需要 partner school，全部阻塞 | 不依赖活动的合作组织或合作学校；最终 UAT 依赖目标使用学校的实际用户 | 先完成内部角色验收、任务脚本、观察表和问题分级规则 | 目标使用学校可安排的学生、教师和管理员，以及真实业务判断 |
| I3.10 生产数据初始化 | 需要 partner school，全部阻塞 | 不依赖合作学校；初始化工具和清单现在可验收，最终值依赖目标部署学校 | 验证学生、教职工、班级、类别、规则、权限、功能开关和学校信息的可重复初始化流程 | 目标部署学校的最终名单、组织结构和配置值 |
| I3.11 切换与回滚计划 | 需要实际学校和日期，全部阻塞 | 计划主体现在可编写；仅日期、责任人和书面批准待定 | 完成学期边界切换模板、通信模板、支持渠道、回滚步骤和决策条件 | 目标部署学校确认的上线日期、责任人和签字批准 |
| I3.12 上线后观察 | 需要 partner school，全部阻塞 | 监控项、阈值、看板和处置手册现在可准备；实际值守在上线后启动 | 配置台账核对、审核 SLA、错误率、上传拒绝率、登录失败监控及告警演练 | 上线日期和具名值守人员 |

上述重分类遵循“可构建部分先完成、机构输入延后填入”的原则。不能因为最终验收需要真实业务输入，就把工具、脚本、模板、监控和技术演练也一并判定为不可开始。

## 6. 对 I3 计划文档的具体改写建议

### 6.1 统一术语

在 `13-Integration-I3-Acceptance.md` 和 `00-Status.md` 中：

- 将含糊的 **real partner school** 改为按语境使用：
  - **target deployment school / 目标部署学校**；
  - **school-provided historical data / 学校提供的历史数据**；
  - **real UAT participants / 真实 UAT 参与者**；
  - **approved go-live date / 已批准上线日期**。
- 保留 **partner organization / 合作组织** 专指活动提案和项目中的组织实体。
- 不再使用“没有合作学校”解释任何活动提案、系统验收或导入机制无法实施。

### 6.2 拆分“工程完成”和“机构确认”

建议将 I3.8-I3.12 每项拆成两个状态：

- **Engineering readiness**：流程、工具、脚本、模板、监控和合成数据演练是否完成；
- **Institutional acceptance**：真实数据对账、真实用户 UAT、最终生产数据、上线批准和上线后值守是否完成。

这样可以准确呈现“技术工作可继续，但最终机构输入尚未到位”，避免把外部依赖误写成整个工作项不可执行。

### 6.3 修订 Gate G5

Gate G5 应区分：

- **进入部署准备前必须完成**：十二个 API 验收场景、双语与响应式页面检查、导入机制演练、初始化流程演练、切换/回滚模板、监控告警演练；
- **正式上线前必须完成**：真实历史台账对账（如适用）、真实用户 UAT、最终生产数据、学校书面批准、G3 恢复演练、G4 负载测试；
- **上线后执行**：I3.12 第一周观察和值守。

I3.12 本身不应作为“上线前已经完成”的条件，否则会形成时间逻辑矛盾；上线前应验收的是监控和处置准备情况。

## 7. 建议的后续执行顺序

1. 修正提案“组织安排”字段的前端控件、请求映射和后端提交校验，包括“选择历史合作组织”与“输入新名称并由后端创建组织 ID”两条路径。
2. 完成 I3.7 场景 #1、#4、#12，并把每个场景的证据逐项记录到 `00-Status.md`。
3. 使用代表性数据完成 I3.8 的导入机制演练和 API 场景 #7；真实台账对账作为部署学校输入到位后的第二阶段。
4. 同步准备 I3.9 UAT 脚本、I3.10 初始化清单、I3.11 切换/回滚模板、I3.12 监控与值守手册。
5. 只有依赖目标部署学校的剩余事项才标记为“等待机构输入”，并明确列出所缺数据、人员、日期或批准，不再笼统标记为“缺少 partner school”。

## 8. 修订后的核心判断

学生发起志愿活动需要完整的发起人、共同组织者、拟邀请指导教师、合作组织和联系人信息。合作组织既可以从历史记录中选择，也可以由学生输入新名称、由后端自动创建并生成新的不透明 `organizationId`；它不需要另一所“合作学校”。I3.7 是现在即可完成的系统验收，I3.8-I3.12 也各有可立即开展的工程准备部分。真正尚未具备的，只能是目标部署学校提供的特定真实数据、参与人员、上线日期和制度性批准，而不是一个由实施计划误引入的“partner school”前置条件。
