# 服务记录表单按来源优化与已确认设计澄清

## 0. 目的与范围

本文件是基于当前前端、后端和数据库实现核查后形成的定稿澄清，规定学生端“提交服务记录”及“编辑退回记录”的表单、接口和数据模型如何按来源区分。它以 `Design/chinese/02-ManualAudit.md` §2.2 为字段基线，但不把证明材料、审核信息和入账信息重复放进“服务信息”步骤：证明材料仍在独立步骤，审核和入账仍由后端审核流程产生。

适用来源仅有两种：

- `PROJECT`：管理员或教师发布、学生已确认报名的正式项目；包括校内活动和校外合作活动；
- `SELF`：学生自主发起服务。

本方案不改变服务记录状态机、审核事件追加写入、附件访问控制或时间币的不可变账务规则。

文中“当前实现”描述已经在代码和迁移脚本中核实；其余内容是本次已经确定、尚待实施的目标设计，不保留中间讨论中的备选方案。

## 1. 已核实的当前实现

### 1.1 前端

`ServiceRecords.tsx` 当前仍提供 `project`、`external`、`self` 三种来源，但后续“服务信息”和“证明材料”使用同一组字段。项目没有选择器；组织名称是自由文本；主管姓名和联系方式也是自由文本。因此，来源选择目前不产生实际的数据约束或差异化体验。本方案要求移除 `external` 来源，并迁移为下述两种来源。

前端也没有“是否包含路途时间”控件，且确认页只显示开始/结束时间，没有显示由时间计算的总时长。

退回记录再提交已经正确地复用原记录并调用 `PATCH`；本次优化必须继续保留这一行为，不能将退回修改变成创建另一条新记录。

### 1.2 后端与数据库

后端在创建和更新时已经以 `endAt - startAt` 计算并保存整数 `durationMinutes`；客户端并不提交时长。`includesTravelTime` 已存在于请求、实体和数据库中，但当前前端没有使用它。

`service_record.id` 是服务端生成的、不可解析的不透明主键。它满足内部唯一性，却不是《人工审核》§2.2/§8.3 所需的、可展示和归档的“服务记录编号”。

现有 `projectId`、`organizationId`、主管姓名和联系方式尚未建立足够的可信关联：项目来源仅检查 `projectId` 是否非空；组织名称仍可由客户端自由提交；主管联系方式由客户端自由填写。项目本身已经持有单个 `organizationId` 和 `ownerId`，其响应也已提供组织名称、负责人姓名；因此，已报名项目的组织与负责人信息应从项目读取，而不是再次由学生填写。数据库已有合作组织的名称、类型、联系人姓名、邮箱、电话和地址，也已有学生和用户的姓名、邮箱字段。

**已确认的实现结论：** 当前 `Project` 没有独立的“校内/校外”字段，也没有组织列表或“第一个组织”的数据结构；`ProjectDto` 只返回一个 `organizationId` 与 `organizationName`。关联 `Organization` 虽有 `type`（如 `SCHOOL`、`COMMUNITY`），但组织类型不能可靠表示活动实际在校内还是校外举行。因此，目前既不能校验“第一个组织必是本校”，也不能以项目字段准确区分校内/校外活动。

## 2. 共同字段与权威规则

所有来源都使用下列共同“服务信息”。其中“后端生成/派生”字段不得由前端写入。

| 字段 | 表单行为 | 权威来源/规则 |
| --- | --- | --- |
| 服务记录编号 | 创建成功后展示，只读；草稿、退回编辑页均展示 | 后端生成 `recordNumber`，数据库唯一约束；不复用、不解析 `id` |
| 服务日期 | 必填 | 实际服务日期，不得晚于当前日期 |
| 开始时间、结束时间 | 必填 | `endAt` 必须晚于 `startAt`；以学校时区转换为 UTC 保存 |
| 总时长 | 只读、随时间即时更新 | 后端以开始/结束时间计算 `durationMinutes`；前端只作同一规则的预览，最终以响应值为准 |
| 是否包含路途时间 | 是/否开关 | 写入 `includesTravelTime`；不进入总时长、不影响入账计算 |
| 路途时间原因 | 选择“是”时必填 | 新增 `travelTimeReason`，仅供审核查看，不记录为服务时长 |
| 服务地点 | 必填 | 项目来源由项目提供且只读；自主发起由学生填写 |
| 服务性质 | 必填 | 现有 `serviceCategoryId`，显示本地化类别名称 |
| 服务描述 | 必填 | 学生实际完成的工作；保留现有长度限制 |

总时长的显示单位为小时，使用分钟整数换算：30 分钟显示 `0.5 小时`、60 分钟显示 `1 小时`、90 分钟显示 `1.5 小时`。数据库仍保存整数分钟，避免浮点精度问题；不限制只能以半小时粒度提交，45 分钟等实际服务时长照实保存和显示。

## 3. 两种来源的表单规则

### 3.1 已发布项目（`PROJECT`，含校内和校外合作项目）

第一步改为“选择学校项目”，只能搜索和选择当前学生有 `CONFIRMED` 报名记录的项目；后端在创建草稿和提交时都重复校验项目存在及该报名关系，不能只信任前端选择器。

选择项目后，以下字段以项目为唯一权威来源，学生只读查看而不输入、不选择：项目名称、项目组织、项目负责人（主管）及其姓名/联系方式快照、服务地点、服务性质和项目时间范围。

学生填写服务日期、开始时间、结束时间、路途时间选项及服务描述。服务地点只读；项目如有分会场，必须由项目管理预设“项目服务点”供选择，不允许学生自由文本覆盖项目地点。项目负责人以 `ownerId` 解析为系统内用户，后端快照其姓名和联系方式；这里不再提供“从教师和学生中另选主管”的控件。

对于校外合作项目，学生同样只从本人 `CONFIRMED` 报名的项目中选择，组织和负责人同样由该项目获得。该步骤不收集证明材料、审核状态、审核人、审核时间或入账数量。

项目的关联数据应存 `projectId`；名称、组织、负责人、类别和地点均保存当时快照，避免未来修改项目后篡改历史服务记录的语义。

### 3.2 自主发起（`SELF`）

保持相对自由：不要求项目或合作组织，填写共同字段、地点、服务性质、服务描述和主管/联系信息即可。允许手工填写外部主管，但其联系方式必填，并明确标示为“待人工核验”。

## 4. 本校组织与项目组织设计

### 4.1 本校组织的定义

系统初始化时必须创建且仅创建一条“本校组织”（`School Organization`）。它是学校自身的组织档案，不是可由用户新增、删除或替换的普通合作组织。

- ID 仍由后端生成不透明字符串；不得把固定值 `1` 当作业务规则，也不得由前端解析 ID；
- `Organization` 新增不可变的 `isSchoolOrganization` 布尔标志；数据库以唯一约束保证最多一条为 `true`；
- 初始化迁移或受控启动任务创建本校组织，名称、地址和学校联系信息从学校设置的初始配置取得；
- 常规组织管理界面不得删除、归档、停用或改写其 `isSchoolOrganization` 标志；学校名称、地址和联系信息可只通过受权限保护的学校设置流程修改；
- 若数据库缺少这条记录，应用启动健康检查应失败或进入受限维护状态，而不能悄悄新建一条来源不明的学校组织。
- **组织列表接口的行为（2026-08-21 已实施，issue 045）：** `GET /organizations`（"合作组织"管理界面及所有基于该接口构建的合作组织选择器的数据来源）永远不返回本校组织这一行；它不是合作方，混入合作组织列表会造成混淆。仍可通过 `GET /organizations/{id}` 按 ID 直接解析到它——只有列表被过滤，不影响按 ID 的直接访问。
- **"受权限保护的学校设置流程"的具体实现（2026-08-21 已实施，issue 045）：** 新增 `GET`/`PATCH /api/v1/school/info`（契约 §4.16），编辑权限判定按**角色代码**而非权限点——仅 `sysadmin` 角色可编辑，`admin` 角色明确排除在外，即使二者自 `V21` 角色合并后持有完全相同的权限集合。未新增权限点：这是刻意的角色级区分，而非普通的 `xxx.manage` 权限检查所能表达的粒度。前端在 System Admin → 系统设置新增独立的"学校信息"卡片（与原"系统信息"卡片中版本号等技术信息分离），仅 `sysadmin` 显示编辑入口；后端同时以角色代码强制校验，非 `sysadmin` 直接调用该接口会收到真实的 `403`，而不仅仅是前端隐藏了按钮。

### 4.2 项目与本校/校外合作组织的关联

每个已发布项目都必须关联本校组织。仅以当前单个 `project.organization_id` 无法同时保存“本校组织 + 校外合作组织”，也无法表达组织角色或顺序。因此需要新建 `project_organization` 关联表，而不是约定“第一个组织”的位置语义。

采用以下字段和约束：

| 字段 | 规则 |
| --- | --- |
| `project_id` | 指向项目 |
| `organization_id` | 指向组织 |
| `role` | `HOST_SCHOOL` 或 `PARTNER` |
| `sort_order` | 仅用于显示排序，不承载业务含义 |

约束：每个项目恰有一个 `HOST_SCHOOL`，它必须引用 `isSchoolOrganization = true` 的组织；零个或多个 `PARTNER` 可引用活跃校外合作组织。`Project.organization_id` 在迁移后应废弃或明确仅作为兼容期的本校/主展示组织，不能继续作为唯一事实来源。

项目还应新增明确的活动地点类型字段，例如 `deliveryScope = ON_CAMPUS | OFF_CAMPUS | HYBRID`。不能用合作组织类型推断它：本校组织可以举办校外活动，校外组织也可能在校园内共同举办活动。

### 4.3 服务记录的项目快照

`PROJECT` 服务记录以 `projectId` 作为关联事实，并在创建时由后端保存项目快照：本校组织、全部合作组织及角色、项目负责人、地点类型、地点、服务性质和项目时间范围。学生不能选择、修改或伪造这些项目归属字段。

## 5. 数据模型与接口调整

### 5.1 服务记录

新增或调整下列持久化字段；所有历史字段继续保留，迁移不得改写已审核记录：

| 字段 | 说明 |
| --- | --- |
| `record_number` | 后端生成、不可变、唯一的展示/归档编号 |
| `travel_time_reason` | `includes_travel_time = true` 时必填；不计入 `duration_minutes` |
| `supervisor_kind` | 枚举：`PROJECT_OWNER`、`INTERNAL_USER`、`STUDENT`、`EXTERNAL_MANUAL` |
| `supervisor_subject_id` | 可空的不透明关联 ID；人工外部主管为空 |
| `supervisor_name`、`supervisor_contact` | 创建或修改时由后端写入的历史快照，而非客户端任意文本 |
| `project_organizations_snapshot` | `PROJECT` 记录保存本校组织、合作组织及角色的不可变快照；`SELF` 为空 |

`duration_minutes` 继续是后端派生字段。前端请求不得出现可写 `durationMinutes`、`recordNumber`、组织类型快照或主管联系方式快照。

### 5.2 请求与响应

创建和更新请求应按来源使用互斥字段，并在后端做一致性校验：

- `PROJECT`：必填 `projectId`；后端从项目解析本校组织、合作组织、负责人、类别、地点与对应快照；禁止客户端指定 `organizationId`/`organizationName`、主管身份或主管联系方式；
- `SELF`：项目和合作组织均为空；
- `includesTravelTime = true` 时必填 `travelTimeReason`；
- 内部主管选择传递 `supervisorKind` 与 `supervisorSubjectId`，由服务端解析快照；

响应新增 `recordNumber`、`travelTimeReason`、主管身份元数据和必要的项目组织快照；仍返回后端计算出的 `durationMinutes`，供确认页与列表显示。

### 5.3 编号生成

不要以“查最大值加一”生成编号，避免并发重复。新增按学年/学生维度锁定的编号序列表；在创建草稿的同一事务中取得序号，构造并持久化 `recordNumber`，再由唯一索引兜底。

编号格式可沿用人工台账的可读语义，例如 `TB-{学年}-{年级}-{学号}-{序号}`，但其中学年、年级和学号均由后端读取学生档案生成。编号一旦产生不随学生后续转班、改名或编辑记录变化。

## 6. 权限、隐私与历史真实性

不能直接扩大现有 `/users/directory` 或 `/students/directory` 的返回字段以暴露全校邮箱/电话：它们现为低敏感目录，且学生可调用。主管选择需要专用的、最小化返回的受控接口，或“先选身份、后由后端在保存记录时解析”的服务层能力。

确定规则：

1. 目录搜索只显示姓名和必要的身份提示；不显示联系方式。
2. 联系方式只在选择后回显给记录提交人及有审核权限的人，并由后端从用户/学生/组织档案快照。
3. 历史服务记录保留主管、组织、类别和地点快照；后续更新通讯录或组织资料不回写历史记录。
4. 若原始档案没有邮箱或电话，保存/提交必须给出明确字段错误，不能静默保存空“自动填充”值。

## 7. 前端交互与迁移顺序

1. 先在 API 契约中定义上述字段、来源互斥规则和错误码；中英文契约同步更新。
2. 后端先建立本校组织、项目组织关联和活动地点类型，再增加服务记录的 Flyway 迁移、实体/DTO、编号服务、来源校验和主管/组织解析；为创建、退回编辑和提交路径补集成测试。
3. 将服务记录来源枚举和 API 契约从 `project/external/self` 收敛为 `project/self`；既有 `external` 记录保留原来源值作为历史兼容数据，不出现在新建表单中。它们可读、可审核；处于 `DRAFT` 或 `RETURNED` 的旧记录沿用原始字段完成一次兼容性编辑和再提交，不得被静默改写为另一来源。
4. 前端将现有单一“服务信息”步骤拆为按 `sourceType` 条件渲染的子表单；项目来源采用“本人确认报名项目”搜索选择器；总时长在开始/结束时间变化时实时预览，并以保存响应的值为准。
5. 退回编辑加载新增字段和历史快照；来源仍锁定，避免把一条已退回的项目记录变成校外或自主记录。
6. 最后更新中英文前端设计文档、`02-ManualAudit.md` 的线上映射说明、实施状态和端到端验收证据。

## 8. 已确认的设计决策

| 决策 | 已确定规则 |
| --- | --- |
| 自主发起的主管 | 允许手工填写外部主管；联系方式必填并进入人工核验。 |
| 服务时长粒度 | 不限制为 0.5 小时；以整数分钟保存、以小时小数显示。 |
| 项目地点 | 学生不得自由修改；分会场必须由项目管理预设为项目服务点。 |
| 服务记录编号 | 首次创建草稿时由后端生成；删除草稿后编号不复用。 |
| 项目组织模型 | 每个项目采用“一个本校组织 + 零至多个合作组织”的 `project_organization` 关联模型。 |
| 校内/校外区分 | 项目新增 `deliveryScope`，取值为 `ON_CAMPUS`、`OFF_CAMPUS`、`HYBRID`，不以组织类型推断。 |

实施顺序固定为：先落地本校组织、多组织项目关联和 `deliveryScope`，再落地项目服务记录快照及两种来源表单；随后更新契约、双语界面、测试和验收证据。

## 9. 验收标准

1. 服务记录只提供“已发布项目”和“自主发起”两种来源，且退回编辑按原来源正确回填。
2. 任意创建/更新请求都不能伪造总时长、展示编号、项目组织数据或已解析主管联系方式。
3. 30 分钟服务在确认页和列表显示为 `0.5 小时`；路途时间选项不会改变 `durationMinutes` 或入账结果。
4. 项目来源只能关联本人已确认报名的项目；篡改 `projectId` 被后端拒绝，项目的本校组织、合作组织、负责人、类别和地点均由项目快照产生。
5. 系统恰有一条不可删除、不可停用的本校组织；每个已发布项目恰有一个 `HOST_SCHOOL` 关联并指向它，校外合作组织仅能以 `PARTNER` 关联出现。
6. 项目负责人及其他允许的主管均能自动获得可审核的联系方式，且目录搜索不向无关用户批量暴露联系方式。
7. `recordNumber` 由后端唯一生成，在并发创建下不重复；历史记录编号和快照均不可被后续编辑改写。
8. 创建、保存草稿、退回修改、提交审核、审核查看和中英文移动/桌面界面均通过端到端验证。

## 10. 对照现有实现复核后的待决问题：方案对比与建议

本节基于对 `frontend/src/app/components/student/ServiceRecords.tsx`、
`cn.timebank.servicerecord`、`cn.timebank.project`、`cn.timebank.organization`、
`cn.timebank.enrollment`、`cn.timebank.iam`（`/users/directory`、`/students/directory`）
现有代码和已生效迁移（截至 `V16`）的复核。§1 的"已核实的当前实现"逐条属实，额外确认：

- **§3.1 的"已确认报名"复用点已经存在，不需要新接口**：`ProjectDto` 已经按 §2.11 的
  "my前缀"约定携带 `myApplicationStatus`（`ProjectCenter.tsx` 已经在用它渲染"已报名/
  待确认/已完成"），且 `GET /applications`（`EnrollmentController`）已经按调用者的数据范围
  自动只返回本人的报名记录，支持 `filter[status]`。"选择本人已确认报名的项目"这一步骤可以直接
  用 `GET /applications?filter[status]=CONFIRMED` 取得 `projectId`/`projectTitle` 列表，
  不需要新建查询能力。

### 10.1 本次建议的实现细节（技术性决定，非业务政策）

| # | 问题 | 方案对比 | 建议 |
| --- | --- | --- | --- |
| D1 | `organization.is_school_organization` 唯一性如何在数据库层面强制？ | (a) 仅应用层"先查后插"检查——实现简单，但两个并发请求之间存在竞态窗口，且这是本项目里为数不多、真正需要"全表至多一条为真"的不变量，仅靠应用层检查不够稳；(b) 在 `is_school_organization` 上加生成列 `school_org_marker`（`true` 时取常量 1、`false` 时取 `NULL`，MySQL 唯一索引允许多个 `NULL`）并对该生成列建唯一索引——数据库层面硬约束，MySQL 8.0.13+ 原生支持，不需要应用层加锁。 | 采用 (b)。数据库约束比应用层检查更可靠，且这条不变量足够重要（错误会导致项目挂靠了两个"本校组织"却无法被应用层逻辑简单发现），值得花一个生成列的成本。`project_organization` 表的 `HOST_SCHOOL` 唯一性（每个项目恰一条）同理，对 `(project_id)` 在 `role='HOST_SCHOOL'` 时的生成列做同样处理。 |
| D2 | `project_organization` 里"每个项目恰有一个 `HOST_SCHOOL`"如何强制？ | 同 D1：(a) 应用层检查 vs (b) 生成列+唯一索引。 | 采用 (b)，与 D1 用同一技术，保持一致性；具体为 `(project_id, CASE WHEN role='HOST_SCHOOL' THEN 1 ELSE NULL END)` 生成列上的唯一索引。 |
| D3 | `recordNumber` 的按学年/学生锁定序列表，具体怎么取号才能避免并发重复且不显式加悲观锁？ | (a) `SELECT ... FOR UPDATE` 锁定序列行，读出当前值+1，再更新——需要显式事务边界，且和 B4.7 项目容量锁定是同一类模式（`ProjectRepository.findWithLockById`），本项目已有先例；(b) 单条 `INSERT INTO record_number_seq (academic_year_id, student_id, seq) VALUES (?, ?, 1) ON DUPLICATE KEY UPDATE seq = LAST_INSERT_ID(seq + 1)`，一条原子语句内完成"取号"，`LAST_INSERT_ID()` 把新值带回应用层，不需要单独的锁定读。 | 采用 (b)。比 (a) 少一次往返、不需要显式管理锁的持有时间，MySQL `INSERT ... ON DUPLICATE KEY UPDATE` 对同一行是原子的，天然避免"两个请求都读到同一个旧值"的竞态。序列表主键为 `(academic_year_id, student_id)`，`seq` 从 1 开始；`recordNumber` 由 `seq` 与学年、年级、学号拼接生成，年级/学号仍如文档所述从学生档案读取，不从序列表本身派生。 |
| D4 | 主管联系方式的"选择后解析"具体走什么接口形状？ | (a) 保持现状：不新增任何联系方式相关接口，学生只提交 `supervisorKind` + `supervisorSubjectId`（内部用户）或手填 `supervisorName`/`supervisorContact`（`EXTERNAL_MANUAL`），后端在创建/更新服务记录的同一次请求里解析快照并随服务记录的响应体一起返回；(b) 新增一个"选中后可预览联系方式"的接口，供学生在提交前先看到"主管张三，电话 138...."再确认——体验更好，但相当于开了一个可被批量探测联系方式的新端点，需要额外的限流/权限设计，且和 §6 "目录搜索不暴露联系方式"的既定原则方向相反。 | 采用 (a)，与文档 §6 第 2 条的原文一致："联系方式只在选择后回显给记录提交人"——"选择后"应理解为"记录已经创建/更新之后"，而不是"选择时的一次额外接口调用"。不新增接口，扩展 `CreateServiceRecordRequest`/`UpdateServiceRecordRequest`/`ServiceRecordDto` 即可。 |
| D5 | 迁移时，现有已发布项目的 `organization_id` 如何回填进新的 `project_organization` 表，`deliveryScope` 默认取什么值？ | (a) 一律假定现有 `organization_id` 就是本校组织，只插入一条 `HOST_SCHOOL`——如果历史项目实际上是校外合作项目，会错误丢失合作组织信息；(b) 不论现有 `organization_id` 是否等于本校组织，都插入本校组织为 `HOST_SCHOOL`；若原 `organization_id` 不是本校组织本身，额外插入一条 `PARTNER` 指向原组织——保留全部历史信息，符合"每个项目恰有一个 HOST_SCHOOL"的新不变量，多余信息好过丢信息；`deliveryScope` 对所有迁移前项目一律回填为 `HYBRID`（含义是"未知/待人工复核"，而不是猜测校内或校外）。 | 采用 (b)。这是纯粹的历史数据兜底策略，不影响任何未来新建项目——新项目在发布时必须显式选择 `deliveryScope`，只有迁移当下已存在的项目才会落到 `HYBRID` 默认值。建议迁移脚本额外输出一份"回填清单"（哪些项目被打上 `HYBRID`/插入了推断出的 `PARTNER` 行），供管理员之后人工复核修正，而不是静默永久生效。 |
| D6 | `SELF` 来源是否仍保留自由文本 `organizationName`？ | 文档 §2 的共同字段表未列出"组织名称"，§3.2 也没有重申保留它，但 §5.1 的字段调整列表里也没有出现"删除 `organization_name`"，且前端列表/详情页（`ServiceRecords.tsx` 的 `rec.projectTitle \|\| rec.organizationName`）现在依赖它做展示兜底。这更像是文档表格遗漏，而不是刻意要删除该字段。 | 保留 `organizationName`（自由文本）作为 `SELF` 来源的可选字段，语义等同于当前 `EXTERNAL` 来源的同名字段；`PROJECT` 来源继续保持"由项目快照决定、客户端不可写"的规则不变。 |
