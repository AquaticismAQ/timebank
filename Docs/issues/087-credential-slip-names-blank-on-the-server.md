# 087 — Chinese names print as blank boxes on the credential slip, on the server only

Status: **Fixed — not yet live-verified**

## Symptom

Every student name on a printed activation slip comes out as a row of empty
rectangles when the PDF is generated by the deployed backend. The rest of the
slip — labels, username, activation code, QR, provenance line — is fine. On a
developer's machine the same code produces the name correctly, so the defect
is invisible to `mvn test`, to a local run, and to code review that trusts
either.

Separately, and not a regression but a gap: the slip was English-only. §2.9
requires the paper and the activation screen to use one vocabulary, and an
admin working in a Chinese interface was handing out English slips.

## Root cause

Two independent problems, one per half of the document.

**1. Names were bitmaps rendered with a host font.** `CredentialSlipDocument`
drew the display name with AWT —
`new Font(Font.SANS_SERIF, Font.BOLD, …)` into a `BufferedImage`, placed into
the PDF as an image. AWT's logical `SANS_SERIF` family resolves against
**system-installed** fonts. Probed on the deployment host directly:

- `new Font(Font.SANS_SERIF, Font.BOLD, 24).canDisplay('李')` → `false`
- `getAvailableFontFamilyNames()` → DejaVu and the logical families, nothing
  else

The host has no CJK font at all, so AWT drew the missing-glyph box for every
character. macOS ships Hiragino Sans GB, so the same call on a build machine
succeeds — which is why the class's own comment confidently described this
path as the *fix* for CJK, and why every test passed while the bug was live.

**2. Labels could not be Chinese at any price.** Labels, username, code and
provenance were Standard-14 `PDType1Font` (Helvetica, Courier). Those are
WinAnsi-encoded and `showText` throws on anything outside Latin-1 — no font
on the host could have changed that. The old code worked around it by folding
a non-Latin-1 issuer name on the provenance line down to the literal
`"an administrator"`.

## Fix

`backend/src/main/resources/fonts/NotoSansSC.ttf` (SIL OFL 1.1, licence
committed beside it) is embedded as a subset in each generated document, and
every human-readable string on the slip is now real PDF text in it. The AWT
text path is deleted. The QR stays an image, because it is one.

| Area | Before | After |
| :--- | :--- | :--- |
| Student name | AWT bitmap, host font | embedded-font text |
| Labels, heading, provenance | Standard-14 Helvetica, English only | embedded-font text, bilingual |
| Username, activation code | Standard-14 Courier-Bold | unchanged — ASCII by construction (§2.5 Crockford, §3.2 8 digits), and a fixed pitch is wanted so `0`/`O` stay apart |
| QR | image | unchanged |
| A CJK issuer name on the provenance line | folded to `"an administrator"` | printed as itself; the fallback now applies only to a genuinely absent name |

Three deliberate choices worth recording:

- **The font file must stay a glyf-based TTF.** The ~8 MB CFF/OTF build from
  the noto-cjk release fails at load with
  `UnsupportedOperationException: OTF fonts do not have a glyf table`.
- **There is no bold.** The bundled file is a *variable* font whose other
  weights live in `gvar` deltas PDFBox does not apply, so its default (and
  only reachable) instance is Regular. The two places that used
  Helvetica-Bold now take their emphasis from size and ink instead; nothing
  fakes a bold by stroking.
- **Glyph coverage is guarded.** `showText` throws on a code point the font
  lacks, which would fail a whole class's download over one unusual name, so
  unmappable code points are substituted with `?` per character.

## Slip language

`CredentialSlipController` already resolved the request's language through
`RequestLanguageService` and `CredentialSlipServiceImpl` already accepted it
as `resolvedLanguage` — it was used for the roster read and then dropped on
the way to the renderer. It is now passed through, so the slip prints in the
language the admin is working in.

**The backend has no message-bundle mechanism for strings it authors itself.**
Its entire i18n is `LanguageResolver` plus `LocalizedNames.pick` over
`name_zh`/`name_en` database columns; API error messages are English-only and
every other user-facing string is rendered by the frontend from
`frontend/src/i18n/*.json`. Rather than introduce Spring's `MessageSource` for
eight labels with exactly one caller, the pairs live in a new `SlipCopy`
record and go through the same `LocalizedNames.pick`, inheriting the same
"anything that is not `en` is Chinese" default. Each value is annotated with
the frontend key it was copied from, per §2.9:

| Slip string | Frontend key |
| :--- | :--- |
| `First time logging in? Use your activation code` / `首次登录？使用激活码` | `auth.login.firstTimeEntry` |
| `Activation code` / `激活码` | `auth.activation.codeLabel` |
| `Username` / `用户名` | `auth.login.accountPlaceholder` |
| `Name` / `姓名` | `admin.students.name`, `student.profile.name` |
| the two scanning instructions, the address-bar line | slip-only; no screen counterpart |

Nothing mechanical keeps the two catalogues in step — the backend cannot read
the frontend's JSON at build time — so the annotation is the link, and it is
stated as such in `SlipCopy`'s javadoc.

## Performance

The font file is 17 MB and the server has 1 vCPU, so the parse is a real
cost. **The bytes are cached, once, for the life of the JVM; the
`PDType0Font` is not**, because a `PDType0Font` owns the subsetting state for
one specific `PDDocument` and writes itself into that document's object
graph. The parsed `TrueTypeFont` underneath is deliberately *not* shared
either: its backing data stream carries a mutable read position and glyph
outlines are pulled from it during `document.save()`, so two concurrent
batches would seek each other's reads.

Measured locally (Apple silicon, warm JVM), a full render including the
per-document font parse:

| Batch | Output | Time |
| :--- | :--- | :--- |
| 1 slip, Chinese | 14.9 kB | ~10 ms |
| 30 slips, Chinese, one per page | 75.5 kB | ~120 ms |
| 45 slips, Chinese, one per page | 107 kB | ~145 ms |

The per-document parse is the ~10 ms floor; the rest is QR generation and
image compression, which is unchanged. With `embedSubset` flipped to `false`
the same 30-slip test run takes 8.3 s instead of 1.3 s and the PDF crosses
17 MB — which is what the size assertion below exists to catch.

## Test plan

The old tests all passed while the bug was live, because they only asked "did
the render throw?" and the build machine had a CJK font. Each new assertion
was **verified red** by reverting the thing it guards, on that same machine:

| Proof | Assertion | Reverted by | Result |
| :--- | :--- | :--- | :--- |
| (a) name is text, not a bitmap | `PDFTextStripper` extracts 同学示例 | reinstating the AWT bitmap path | 4 tests red |
| (b) Chinese labels present | extracts 首次登录？使用激活码, 激活码, 姓名, 签发人：, 有效期至： | forcing `SlipCopy` to English | 2 document tests + 1 service test red |
| (c) font is subset | 30-slip PDF < 1 MB, embedded `FontFile2` < 500 kB, exactly one program per batch | `embedSubset` → `false` | red |
| (d) no dependence on host fonts | ArchUnit: no `java.awt.Font`/`FontMetrics`/`Graphics`/`Graphics2D`/`RenderingHints`/`java.awt.font..`; plus, from the PDF itself, exactly one image XObject per single-slip page and a `PDType0Font` whose `BaseFont` names the bundled file with a real embedded `FontFile2` | reinstating the AWT bitmap path | both red |

`mvn clean test`: 229 tests, 0 failures.

**What (d) does and does not prove.** The real condition cannot be forced —
macOS cannot be made to forget Hiragino Sans GB — so this is structural on
purpose. The ArchUnit half proves the slip builder has no way to *ask* which
fonts are installed; the runtime half proves the finished document carries
its own glyph program, so a viewer on a font-less host has everything it
needs. Neither proves PDFBox has no internal fallback of its own (that is
PDFBox's code), and neither proves the page looks right on the server. Only a
live download does that, and it has not been done.

Also verified by rendering slips to PNG locally and looking at them: Chinese
and English, one-per-page and two-per-page, heading and name clear of the QR,
provenance line intact under the cut guide.

## Known limitation: text extraction aliases some characters

PDFBox builds a subset font's `ToUnicode` map by reversing the font's own
character map and taking the lowest code point that reaches each glyph. In a
pan-CJK font a glyph is reachable from both the CJK ideograph and its Kangxi
radical twin, and the radical block sits lower — so 示 (U+793A) extracts as
⽰ (U+2F70). The **drawn glyph is correct**; only copy-out and in-viewer
search are affected. NFKC folds most of these back (the tests normalise on
both sides), except variant pairs that are not compatibility-equivalent:
用户名 extracts as 用戶名, because 户 and 戶 are separate code points sharing
one glyph. Not worked around in the product — it is PDFBox's behaviour, it
does not affect what a printer puts on paper, and any fix would mean editing
the font's cmap.

## Resolution

- `backend/src/main/java/cn/timebank/iam/application/CredentialSlipDocument.java` — AWT text path deleted, embedded font, bilingual copy, auto-fitting, glyph guard.
- `backend/src/main/java/cn/timebank/iam/application/SlipFont.java` — new; cached font bytes, per-document subset embed.
- `backend/src/main/java/cn/timebank/iam/application/SlipCopy.java` — new; the bilingual literals and where each came from.
- `backend/src/main/java/cn/timebank/iam/application/CredentialSlipServiceImpl.java` — passes the already-resolved language to the renderer.
- `backend/src/test/java/cn/timebank/iam/application/CredentialSlipDocumentTest.java` — the four proofs above.
- `backend/src/test/java/cn/timebank/iam/application/CredentialSlipServiceTest.java` — the language reaches the document, both directions.

The endpoint contract, batch-selection rules, audit behaviour and
`ActivationService` are untouched. No new configuration key was needed.

*Verified by `mvn clean test` (229 passing), by reverting each new assertion
and confirming it goes red, and by eyeballing locally rendered PNGs of the
