# 时间银行 · 前端设计方案（Frontend Design）

> 本文档定义时间银行第二阶段 Web 前端的顶层功能、页面划分与操作流程，并为第三阶段 POV 微信小程序和第四阶段价值拓展预留前端入口。本文不包含组件代码、视觉稿或具体 API 字段；接口边界见 `APIContract.md`。

---

## 1. 建设目标

第二阶段采用**前端驱动（Frontend-Driven）**的实施方式：先确定用户任务、页面结构、状态与接口需求，再由后端围绕稳定的 API 合约提供能力。

前端必须满足以下目标：

- 仅依靠 Web 即可跑通“项目发布—学生报名—服务记录—审核—时间币入账—进度统计—复核”的完整流程。
- 提供清晰独立的**学生入口**与**管理入口**；管理入口根据管理员、学生发展中心和教师权限展示不同功能。
- 使用 **React + Tailwind CSS** 实现，采用移动优先的响应式设计，同时保证桌面端管理效率。
- 第二阶段不依赖微信、企业微信、钉钉或其他 IM。
- 所有业务能力通过版本化 **RESTful API** 获取，不在前端复制业务规则。
- 为第三阶段 POV 和第四阶段兑换、借贷、增值功能预留导航、路由、权限和功能开关。
- Modern style, Mobile first, theme based UI support dark/light time based auto/manual switch and system mode
- Each table/list should have a search, sort and filter functionality. Use card view for better mobile experience if needed like the table have too many columns.
- Text input area should have default height(10 rows), monospace font, auto line wrap and vertical scroll

## 2. 技术与交互原则

### 2.1 技术边界

| 项目 | 约定 |
| --- | --- |
| 前端框架 | React |
| 构建工具 | Vite |
| 样式体系 | Tailwind CSS |
| 终端策略 | Mobile First，逐级增强至平板和桌面 |
| API | RESTful API，统一使用 `/api/v1` 版本前缀 |
| 身份认证 | Web 会话或短期访问令牌，由后端统一管理 |
| 权限 | 后端权限为最终依据；前端仅负责按权限隐藏、禁用和引导 |
| 文件 | 通过受控上传接口或对象存储短时上传凭证提交 |
| 通知 | 第二阶段使用站内通知，不依赖 IM |
| 扩展控制 | Feature Flag + 权限码 + 阶段配置 |

### 2.2 设计原则

- **任务优先**：首页首先展示用户下一步应做的事情，而不是堆叠统计数字。
- **移动优先**：学生高频操作优先适配单手操作、弱网和小屏；教师批量审核在桌面端增强。
- **渐进披露**：默认呈现必要字段，高级筛选、审计信息和规则配置按需展开。
- **状态可见**：项目、报名、服务记录、审核和账户流水均明确展示当前状态、下一步和责任人。
- **不可逆操作可控**：驳回、关闭项目、冲正账户等操作必须二次确认并填写原因。
- **草稿安全**：长表单支持自动保存草稿、离开提醒和失败重试。
- **可追溯**：详情页统一提供时间线，展示提交、退回、补充、审核和入账过程。
- **无障碍与可读性**：颜色不作为唯一状态标识；表单具有明确标签、错误说明与键盘可操作性。

## 3. 用户角色与入口

### 3.1 角色

| 角色 | 主要范围 |
| --- | --- |
| 学生 | 浏览项目、报名、提交服务记录、查看审核和账户、申请补录或复核 |
| 教师 | 管理被授权项目，审核所属年级/班级记录，查看本数据范围统计 |
| 学生发展中心管理员 | 管理全校项目、组织、审核、规则、账户和统计 |
| 系统管理员 | 管理账号、角色、权限、系统参数、数据导入导出与审计日志 |

以上四行为预置默认角色，而非固定不变的集合——学生、学生发展中心管理员（"Admin"）、系统管理员为受保护角色（不可删除），教师及学校自定义的其他教职工角色均为普通、可配置角色，可在管理端「角色」页面创建与配置（见 `07-RoleFinetune.md`）。本轮系统管理员本身刻意不在该页面中展示——它仍正常存在并生效，只是尚未在界面中开放管理。

每个用户始终且仅持有一个角色（见 `07-RoleFinetune.md` §2.5，已取代下方早期的多角色/入口选择设计）。登录后：

- 学生角色账号直接进入学生入口。
- 其他任一角色（教师、学生发展中心管理员、系统管理员，或学校自定义角色）直接进入管理入口。

不存在入口选择页，也没有工作区切换——角色唯一确定账号所对应的入口，且在账号存续期间固定不变。

### 3.2 登录入口

统一登录页提供：

- **登录名**输入，且仅此一种标识。学生使用系统生成的 8 位数字登录名，教职工保留 `teacher001` 形式的命名账号。**不接受**学号、工号或邮箱——同一个输入值可能同时命中甲的登录名与乙的学号，以优先级回退匹配存在登入他人账号的风险（见 `Docs/optimization/10-StudentIdentityAndOnboarding.md` §2.1–2.2）。登录名比对不区分大小写。
- 密码输入与显示/隐藏。
- **首次登录入口**：“首次登录？使用激活码”，跳转至激活页（§3.2.1）。该文案是固定的，必须与纸质凭证单上的用词**逐字一致**——学生需要据此把纸和屏幕对应起来（方案 §2.9）。
- “记住此设备”选项。
- 忘记密码入口。对学生而言该入口指向操作指引而非自助重置：由管理员重新签发激活码与新的凭证单，服务端始终不生成密码（方案 §2.4、§3.7）。
- 隐私政策、使用条款与未成年人信息处理说明。
- 登录失败、账号锁定、密码过期和系统维护状态提示。

### 3.2.1 首次激活页

位于 `/activate` 的公开页面，有两条到达路径：点击登录页的首次登录入口，或扫描纸质凭证单上的二维码——后者以 `/activate?code=…` 深链进入并自动填入激活码。

该页一步完成激活码录入与学生自设密码。激活码输入框在录入过程中即时规范化：转为大写、去除打印分隔符，并按 Crockford 规则折叠易混字符（`I`/`L` 折为 `1`，`O` 折为 `0`），使误读纸面的输入仍可成功。

由于导入账号在激活前**根本不存在密码**，凭证单送达学生之前账号不可能被使用。激活码单次使用且限期有效（默认 7 天，可配置并打印在凭证单上）；逾期未使用的账号进入独立的“已过期”状态，而非“已锁定”，以便管理员区分“凭证单未领取”与“被暴力破解锁定”。

第二阶段不提供微信扫码或其他 IM 登录。学校统一身份认证可作为后续可选能力，但不得影响账号密码登录的独立可用性。

### 3.3 登录后公共功能

所有角色共享：

- 当前用户、角色和数据范围展示。
- 站内通知中心。
- 个人资料与安全设置。
- 修改密码、退出登录。
- 帮助与规则说明。
- 无权限、会话过期、网络异常和系统维护页面。

## 4. 全局信息架构

### 4.1 学生入口导航

移动端底部导航建议固定为：

1. **首页**
2. **项目**
3. **记录**
4. **账户**
5. **我的**

“通知”“复核/补录”“达标进度”等功能通过首页卡片和“我的”进入。第三、第四阶段入口按功能开关插入相应业务区域，不随意增加底部主导航数量。

桌面端使用左侧导航，内容保持同一信息架构。

### 4.2 管理入口导航

管理入口桌面端采用可折叠左侧导航：

1. 工作台
2. 项目与报名
3. 审核中心
4. 学生与组织
5. 时间币账户
6. 统计与报表
7. 通知
8. 数据管理
9. 系统管理

移动端管理入口采用顶部标题、抽屉导航和底部主要操作按钮。复杂批量任务提示用户切换至较大屏幕，但不得完全阻断必要的单条审核。

## 5. 学生入口页面

### 5.1 学生首页

首页聚合：

- 当前(和历史)学年服务时长、累计时间币和阶段达标进度。
- 待办事项：待补充记录、待确认报名、活动提案反馈、复核结果、未读通知。
- 正在报名或即将开始的项目。
- 最近服务记录及审核状态。
- “提交服务记录”和“发起志愿活动”主要操作按钮。
- 规则更新、截止日期和学校公告。

### 5.2 项目中心

#### 项目列表

- 按服务类别、日期、地点、年级、报名状态筛选。
- 支持关键词搜索和“仅看可报名”。
- 项目卡展示名称、时间、地点、剩余名额、认定时长和报名截止时间。
- 空状态区分“暂无项目”和“筛选无结果”。

#### 项目详情

- 项目介绍、任务、时间地点、组织方、负责人、适用年级和安全说明。
- 名额、报名期限、候补规则、证明要求和认定时长。
- 当前学生报名状态与可执行操作。
- 报名、取消报名或加入候补。

#### 我的报名

- 按待确认、已报名、候补、已完成、已取消分组。
- 展示报名状态时间线和项目变更通知。
- 项目完成后直接发起关联服务记录。

### 5.3 发起志愿活动

学生可向学校提交面向其他学生开放的志愿活动提案。该能力用于申请成为活动发起人或学生负责人，不代表学生可以直接发布正式项目。

#### 我的活动提案

- 按草稿、待审核、需修改、已批准、已驳回、已撤回筛选。
- 展示活动名称、计划日期、本人角色、当前审批节点和最后更新时间。
- 已批准提案显示关联的正式项目及后续筹备入口。

#### 新建/编辑活动提案

采用分步表单：

1. **活动概述**：名称、公益目标、服务类别、活动说明和预期成果。
2. **实施计划**：时间、地点、活动形式、预计时长、人数、参与对象和志愿任务。
3. **组织安排**：学生发起人、共同组织者、拟邀请指导教师、合作组织和联系人。
4. **安全与资源**：风险与安全措施、物资、场地、预算或其他支持需求。
5. **招募与认定**：招募方式、报名条件、名额、服务证明方式和建议认定时长。
6. **确认提交**：完整摘要、真实性声明和提交。

行为要求：

- 支持保存草稿、复制既有提案和预览。
- 提交后进入教师/管理员审批，不直接出现在项目中心。
- 审批人可要求修改；学生在原提案上形成新修订版本后重新提交。
- 学生可在审批开始前撤回；审批开始后需提出撤回请求。
- 批准后由系统生成正式项目草稿，学生发起人被记录为学生负责人，指导教师或管理员仍是正式项目责任人。
- 正式项目必须由具有 `projects.publish` 权限的教师或管理员确认并发布。

#### 活动提案详情

- 展示完整提案、修订版本和附件。
- 展示审批状态、负责教师、反馈意见和时间线。
- 可用操作：编辑草稿、提交、按意见修改、撤回、复制提案。
- 批准后展示关联项目、本人组织职责和项目筹备进度。

### 5.4 服务记录

#### 记录列表

- 按草稿、待审核、退回补充、审核中、通过、驳回筛选。
- 支持按日期、项目、组织和学年搜索。
- 每条记录展示服务日期、项目/服务名称、申报时长、审核状态和入账结果。

#### 新建/编辑记录

采用分步表单。记录来源只有两种可选类型，创建时一次性确定，之后不可更改（见 `Docs/optimization/03-ServiceRecordFormOptimization.md`）：

1. **来源**：选择"已报名项目"（学生对该项目持有已确认的报名）或"自主发起"（学生自行组织，不关联项目）。第三种来源"校外"（早于本次设计）仅作为历史数据可查看/编辑/重新提交，绝不作为新记录的可选项出现。
2. **服务信息**：日期、开始/结束时间（含实时时长预览）与描述为两种来源共有。若为**已报名项目**，组织、服务性质与地点均为只读，直接取自项目本身——学生无需也不能自行填写。若为**自主发起**，学生自行填写地点、可选的组织名称与服务性质。两种来源均提供路途时间披露开关，开启后须填写原因。
3. **证明材料**：若为已报名项目，主管（即该项目的负责人）以只读方式展示。若为自主发起，学生需先选择主管类型——校内教职工或另一名学生（通过真实目录搜索选定，联系方式由服务端解析）或外部人员（直接填写姓名与联系方式）——再上传证明材料。
4. **确认提交**：展示完整摘要（含实时时长预览）、声明与提交动作。记录的永久编号在保存时生成，保存后在列表/详情页展示，本页不显示。

行为要求：

- 提供草稿保存和自动保存反馈。
- 前端进行必填、格式、时间范围和文件类型校验。
- 后端返回的业务校验错误定位到具体步骤和字段。
- 提交后进入只读详情；退回补充时创建新的修订版本，且来源锁定不变（已报名项目来源的退回记录不能在重新提交时变为自主发起，反之亦然）。

#### 记录详情

- 服务信息和材料预览。
- 审核状态、审核意见和入账数量。
- 全流程时间线。
- 可用操作：编辑草稿、补充材料、撤回、申请复核。
- 已通过记录展示关联账户流水和存证状态（如启用）。

### 5.5 达标进度

- 当前年级年度要求、阶段要求、已完成、审核中和缺口。
- 按服务类别和学年拆分。
- 展示规则来源和最近更新时间。
- 对临近节点未达标情况给出行动入口，而非仅显示警告。

### 5.6 时间币账户

- 当前余额、累计获得、累计兑换、冻结和借入数量。
- 流水列表：入账、冲正、冻结、解冻、兑换、借入、归还。
- 流水详情展示来源记录、变动前后余额、时间和说明。
- 第二阶段若第四阶段功能未启用，兑换与借贷入口显示"暂未开放"，不显示虚假可操作按钮。

### 5.7 案件：补录、复核与人工调整

学生可发起两类案件——**补录**（材料补充）与**复核**（申诉/异议）；第三类**人工调整**属于同一套统一案件模型，但仅限工作人员发起，学生侧无入口。

- 可从相关服务记录发起以避免重复填写公共信息，也可不关联具体记录、以一般性案件的形式发起（例如并非针对某一条记录的复核）。
- 补录需选择原因并上传补充证明；复核需填写异议说明。
- 三类案件共用同一状态模型：`草稿 → 已提交 → 审核中 → 已解决`，另有 `审核中 → 需补充信息 → 重新提交`（要求补充后再次提交）与 `审核中 → 已驳回` 两条分支。
- **我的申诉**：独立的个人案件历史列表，汇总本人发起的全部案件（不局限于某条记录），展示类型、状态及处理意见/时间线。

### 5.8 通知与个人中心

- 站内通知按审核、项目、账户、规则和系统分类。
- 支持已读/未读与跳转到相关业务详情。
- 个人中心展示基础资料、班级年级、隐私授权状态和安全设置。（系统**不保存**监护人信息——相关列已在 `V26` 中按数据最小化原则删除，见 `Docs/optimization/08-SecurityPrivacyHardening.md` §3.1。）
- 学号、年级等权威字段不可由学生直接修改，需联系管理员。

## 6. 教师入口页面

教师使用管理入口，但只能访问授权项目和年级/班级数据。

### 6.1 教师工作台

- 待初审、待复核、即将超时记录。
- 待评估的学生活动提案和待确认的提案修改。
- 所负责项目报名与完成情况。
- 所属学生达标概览和未达标名单。
- 最近退回、驳回及异常记录。

### 6.2 项目与报名

- 创建或维护有权限的项目草稿。
- 提交项目发布或由有权角色直接发布。
- 查看报名名单、候补、取消和完成状态。
- 批量导出名单和导入签到/完成结果。

### 6.3 学生活动提案审批

- 待审批列表按提交时间、计划活动日期、年级和审批 SLA 排序与筛选。
- 提案详情展示公益目标、实施计划、学生组织者、参与对象、安全方案、资源需求、建议时长和全部修订记录。
- 评估教育价值、公益性、可行性、安全性、时间认定、场地冲突和资源需求。
- 操作为要求修改、批准或驳回。审批为单层直接决定——持有提案审批权限的账号（教师、学生发展中心管理员或系统管理员）均可直接决定，不设"先推荐批准、再转交终审"环节。
- 要求修改或驳回时必须选择标准化原因并填写具体意见。
- 批准会在同一事务内自动生成正式项目草稿并回填提案的 `approvedProjectId`；批准后接管或协助完善该草稿，确认学生负责人职责、指导教师和发布计划。
- 审批时间线对提案学生可见，但内部备注仅对有权人员可见。

### 6.4 审核工作台

#### 审核列表

- 默认按紧急程度和提交时间排序。
- 按状态、年级、班级、项目、组织、日期和异常标记筛选。
- 桌面端支持批量选择；移动端以单条处理为主。

#### 审核详情

- 学生与服务信息。
- 材料预览。
- 重复记录、异常时长和规则校验提示。
- 历史修订、审核与账户影响时间线。
- 操作：通过、退回补充、驳回、转交复核。
- 每个决定必须记录审核意见；驳回必须选择标准化原因。

### 6.5 学生进度与报表

- 查看权限范围内的学生列表和达标进度。
- 查看学生服务历史和账户流水只读视图。
- 生成班级/年级统计并导出。
- 向指定学生发送站内提醒。

## 7. 管理员入口页面

管理员包含学生发展中心管理员和系统管理员。两者共享管理框架，权限不同。

### 7.1 管理工作台

- 全校项目、报名、审核、账户和达标指标。
- 待处理的学生活动提案、其他审核任务、异常趋势和审核 SLA。
- 数据导入结果、系统告警和近期关键操作。
- 可按学年、年级和时间范围切换。

### 7.2 项目、报名与组织管理

- 项目全生命周期：草稿、发布、报名中、进行中、结束、关闭。
- 项目模板、服务类别、时长规则、报名和候补规则。
- 组织方档案、联系人、资质状态和历史项目。
- 报名名单批量处理、导入导出与变更记录。

### 7.3 学生活动提案审批管理

- 全校活动提案队列及待修改、已批准、已驳回和已撤回视图。
- 分配评审人并监控审批 SLA。审批为单层直接决定：任一持权限账号均可直接批准/驳回，不设"推荐后转交终审"环节。
- 查看提案修订差异、教师意见、内部备注、场地冲突、资源占用和同类历史活动。
- 执行要求修改、批准或驳回；批准后生成正式项目草稿并指定指导教师、学生负责人和发布责任人。
- 处理批准后的重大变更：退回项目草稿重新审批或撤销尚未发布的批准，所有操作保留审计记录。
- 配置提案提交窗口、适用年级、必填材料、审批层级、审批 SLA 和学生发起活动数量上限。

### 7.4 审核中心

- 全校服务记录审核队列，以及异常记录。
- 独立的案件队列，涵盖复核、补录与仅限工作人员发起的人工调整——拥有自己的队列与详情工作台，与上述服务记录队列分离，但共用统一案件状态模型（见 §5.7）。
- 审核任务分配与转交。
- 批量通过仅适用于满足配置条件的低风险记录。
- 查看完整证据、历史版本、审核意见和操作日志。
- 对已通过记录执行冲正，而不是直接改写或删除。

### 7.5 学生与基础数据

- 学生、班级、年级与学年管理。（不含监护人信息——已在 `V26` 中删除，见硬化方案 §3.1。）
- 单条维护与批量导入。
- 转班、升年级、毕业、停用等状态变更。
- 学生账号重置、解锁和角色检查。

### 7.6 时间币账户

- 查询账户和流水。
- 冻结、解冻、人工调整和冲正。
- 人工操作必须填写原因、关联记录并通过权限校验。
- 余额不可直接编辑；所有变化均生成不可覆盖的流水。
- 第四阶段启用后管理兑换、借贷和增值规则。

### 7.7 规则配置

- 年级年度与阶段时长要求。
- 时间币换算单位和最小记录单位。
- 服务类型、每日/单次上限。
- 审核状态、审核 SLA 和复核规则。
- 文件要求、允许格式和大小。
- 功能开关及生效时间。
- 规则发布前提供影响摘要；历史规则只读保留。

### 7.8 统计与报表

- 参与率、达标率、服务总时长、审核效率、数据完整率等指标。
- 按学年、年级、班级、项目、组织和服务类别下钻。
- 报表导出作为异步任务执行，并在完成后通过站内通知下载。
- 统计口径页面展示指标定义和数据更新时间。

### 7.9 数据与系统管理

- 历史台账导入：上传、字段映射、预校验、错误下载、确认导入和结果审计。
- 学生名册导入，以及随之而来的激活凭证单签发（§7.9.1）。
- 数据导出与学年归档。
- 用户、角色、权限和数据范围。
- 登录日志、操作日志、异常日志。
- 系统参数、站内通知模板和维护模式。

### 7.9.1 激活凭证单

仅管理员可用（方案 §2.10）。该界面紧接名册导入之下，因为这正是需要它的时刻：
导入生成待激活账号，而此处把这些账号变成学生可以拿在手里的东西。教师没有签发
入口，本班也不例外，因此该操作不放在教师同样会使用的页面里。

选定班级后，界面会在签发任何激活码**之前**说明将生成多少张凭证单，并按从未激
活、激活有效期已过、已激活（跳过）、名册中尚无账号（跳过）分项列出。三十人的
班级只生成四张凭证单是正确行为而非故障，分项数据正是用来说明这一点的。

签发属于破坏性操作，界面也照此呈现：它会为计入的每位学生签发新激活码，从而作
废该学生当前持有的激活码，于是本班此前已打印并发放的凭证单立即失效。该后果在
按钮被按下之前就以内联方式说明，并在确认步骤中再次说明——确认框会写明班级与数
量，且不能通过点击背景关闭。每页凭证单数按其本来的封闭取值呈现——1 或 2，默认
1（方案 §2.8）——界面同时说明激活码会过期、须尽快发放（方案 §2.6）。

## 8. 第二阶段核心操作流程

### 8.1 项目发布与报名

```text
教师/管理员创建项目草稿
→ 完善时间、地点、名额、服务任务和认定规则
→ 发布
→ 学生在项目中心报名
→ 系统按规则确认或进入候补
→ 教师查看并管理名单
→ 项目结束后学生从报名记录发起服务记录
```

### 8.2 学生发起活动与审批

```text
学生创建活动提案草稿
→ 填写活动目标、实施计划、组织安排、安全措施和招募方案
→ 提交审批
→ 教师/管理员评估（单层决定——任一持权限账号均可直接决定）
   → 要求修改：学生按意见创建新修订并重新提交
   → 驳回：记录标准化原因和说明
   → 批准：在同一事务内自动生成正式项目草稿、回填 approvedProjectId 并指定责任教师
→ 教师/管理员完善项目规则并正式发布
→ 其他学生在项目中心报名
→ 学生发起人通过项目页面参与筹备和名单协作
```

学生发起人只能访问被明确授权的项目筹备信息，不能自行修改审核规则、批准报名、认定时长或发布项目，除非另行授予相应权限。

### 8.3 自主服务记录与审核

```text
学生新建记录并保存草稿
→ 填写服务信息和上传证明
→ 确认提交
→ 教师审核
   → 通过：生成时间币流水并更新达标进度
   → 退回：学生补充材料并重新提交
   → 驳回：记录原因，学生可发起复核
→ 学生查看结果、账户与进度
```

### 8.4 案件：复核 / 补录 / 人工调整

```text
学生发起复核或补录案件（从记录详情或独立发起）
→ 填写异议/原因并补充材料
→ 进入案件队列（草稿 → 已提交 → 审核中）
→ 已解决（维持原决定 / 改为通过） / 需补充信息（学生补充后重新提交） / 已驳回
→ 系统通知学生并在该案件自己的时间线留痕；同时可在"我的申诉"中查看
```

第四条路径——工作人员发起的**人工调整**——共用同一队列与状态模型，但无学生侧发起入口，用于工作人员直接更正台账而非响应学生申请的场景。

### 8.5 历史台账导入

```text
管理员下载模板
→ 上传历史台账
→ 系统解析并预校验
→ 管理员查看汇总与逐行错误
→ 修正后重新上传或确认有效数据
→ 后台异步导入
→ 生成服务记录、账户流水和导入审计报告
```

## 9. 第三阶段扩展预留：POV

第二阶段 Web 前端预留以下能力，但默认由功能开关关闭：

### 9.1 学生侧预留

- “现场 POV”入口及 POV 记录状态。
- Web 服务记录详情中的“POV 证据”只读区域。
- 见证、组员互证、监护人背书和 AI 初审状态时间线。
- 从 Web 查看小程序提交的 POV 记录和复核结果。

### 9.2 管理侧预留

- POV 审核队列。
- AI 风险分、风险标签和证据元数据区域。
- 随机抽查任务、见证者核验结果和公示质疑处理。
- 白名单基地与见证者信用管理。
- 存证状态和 TxHash 查看入口。

### 9.3 边界

- 小程序负责现场采集；Web 负责完整管理和人工处置。
- 小程序不可创建独立账户余额或独立审核状态。
- POV 数据通过同一 `/api/v1` 资源体系接入。

## 11. 响应式布局与关键组件

### 11.1 断点策略

- 手机：单列、底部导航、卡片列表、底部操作区。
- 平板：双列详情或列表+筛选。
- 桌面：固定侧栏、数据表格、列表与详情并排、批量操作。

具体断点采用 Tailwind CSS 统一配置，业务页面不得自行定义不一致的断点体系。

### 11.2 共用界面模式

- 应用外壳、页面标题和面包屑。
- 状态徽标与状态时间线。
- 搜索、筛选抽屉、排序和已选条件。
- 数据表格与移动端卡片列表。
- 分步表单、文件上传和材料预览。
- 确认对话框、底部操作面板和原因填写。
- 空状态、骨架屏、错误状态和重试。
- 站内通知、Toast 与全局任务进度。

### 11.3 统一状态语言

同一业务状态在所有页面使用统一名称、颜色和说明。页面不得自行创造“处理中”“审核中”等近义状态；状态定义以 `APIContract.md` 为准。

## 13. 前端驱动的交付顺序

1. 建立页面地图、角色权限矩阵和统一状态词典。
2. 建立 React/Tailwind 应用外壳、登录、路由、权限门禁和 Mock API。
3. 优先贯通学生提交记录与教师审核的最小闭环。
4. 加入项目报名、账户流水和达标进度。
5. 完成管理员基础数据、规则、导入导出和审计能力。
6. 对接真实 RESTful API，以合约测试替换 Mock。
7. 完成移动端、桌面端、异常状态、权限和全流程验收。
8. 保留第三、第四阶段路由和权限入口，但在功能开关关闭时不加载对应模块。

## 14. 第二阶段验收标准

- 学生、教师和管理员可通过独立账号登录并直接进入正确入口（无入口选择页，无工作区切换）。
- 权限不足时前端不展示入口，直接访问路由也由后端拒绝。
- 学生能够完成项目报名、记录提交、材料补充、复核和结果查询。
- 学生能够创建、提交、修改、撤回活动提案，并查看审批意见及关联正式项目。
- 教师能够完成项目管理、报名管理、学生活动提案评估、记录审核、退回和进度查看。
- 管理员能够管理活动提案审批规则和队列，并管理全校基础数据、规则、账户、统计、导入导出和审计日志。
- 审核通过会产生账户流水并自动更新学生进度。
- Web 在不接入微信及其他 IM 的情况下可以完整运行。
- 手机端完成所有学生核心任务；桌面端支持教师与管理员的高效批量操作。
- 网络失败、重复提交、会话过期、文件失败和并发修改均有明确反馈与恢复路径。
- 第三、第四阶段入口由功能开关控制，不影响第二阶段稳定性。
