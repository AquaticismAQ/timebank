# Integration Test Status

> Living document — the record of what's been live-tested against the real shared test server (`https://tb.example.com/`), what real bugs that testing found, and what was done about them. Update this whenever a live-verification session against the real backend finds or fixes something — not a burst rewrite before a review. `Docs/implementation/00-Status.md` tracks build *phases* (B0–B7, I0–I3); this file tracks the ongoing activity of actually using the real, deployed app with real data and real accounts, which continues after every phase is "done."

## 1. Current dataset status

Seeded via `integration-test/seed.ts` on **2026-08-07**. See `README.md` for how to re-run and `MOCK_DATA_GUIDE.md` for the dataset's shape. Snapshot as of that run:

- 5 organizations, 5 login accounts (`admin001`/`teacher001`/`student001`/`student002`/`both001` — see `Docs/TestAccounts.md` for current passwords), 10 students (3 with logins, 7 roster-only).
- 6 projects covering every lifecycle status (`draft`/`published`/`registrationOpen`/`inProgress`/`completed`/`closed`), plus a 7th `draft` project auto-generated from an approved proposal.
- 8 service records covering every review status (`draft`/`submitted`/`approved`/`returned`), with real ledger credits and real notifications as side effects of the approvals.
- 4 event proposals covering every review status (`draft`/`submitted`/`changesRequested`/`approved`).
- `teacher001` holds a real `GRADE`-scoped `teacher_scope_assignment` (grade_10, `serviceRecords`+`eventProposals`) — can review the three grade-10 linked students, 404s on anyone outside that scope.

Not yet exercised by any seed or live session: Cases/appeals workflow (`CaseReview.tsx`/student appeal modal), account freeze/unfreeze, bulk review actions, notifications beyond the ones service-record/proposal decisions generate as a side effect, reports/dashboards under real load.

## 3. Findings / known constraints (not bugs — noted so they don't get rediscovered)

- `event_proposal.format` is `VARCHAR(32)` — a natural-language format description longer than that truncates the INSERT (`MysqlDataTruncation`), surfaced to the API caller as an opaque `500`. The real stack trace is only visible in the server's own `journalctl -u timebank-backend`, not in the API response. Keep `format` short (a label, not a sentence) in any new seed data or real proposal.
- No student-creation UI exists anywhere except bulk CSV import (`students` import type, bug #3 above) — there is no `POST /students` call site in the frontend at all. A single-student "add student" form is a real, still-open gap if that's ever needed.
- `ProfilePage.tsx` (student) requires both `progress` and `account` to resolve before rendering anything past a bare loading placeholder — a brand-new student with zero service records has no `account` row yet (`GET /accounts/{id}` 404s until the first credit lazily creates it), so their "我的" page is silently blank forever. Named, not fixed — out of scope when found (see `Docs/TestAccounts.md`'s account-creation notes).
- **2026-08-08 live-verification of the new Cancel-and-archive/archive-gate feature permanently archived three real seeded projects**: "School Library Organization and Classification" (archived via the normal gate-checked path — it had zero confirmed enrollments, so the gate passed vacuously), and "Nursing Home Visit and Care Activity" / "Example District C Community Environmental Cleanup" (archived via the new `cancel` override, to prove that action end-to-end through the real UI). There is no un-archive action by design (matches the `rules`-module precedent already noted in `backend-design-status` memory of a throwaway-test action being genuinely irreversible) — the seeded dataset now has three fewer non-archived demo projects than `README.md`/`MOCK_DATA_GUIDE.md` describe. Re-seed if a fresh, fully-non-archived dataset is needed for a future demo.
